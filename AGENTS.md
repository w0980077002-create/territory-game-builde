# TERRITORY — инструкция исполнителю

## Задача и самостоятельность

Последнее прямое поручение владельца определяет задачу и важнее этого файла. Владелец делегировал техническое управление репозиторием: самостоятельно исправлять, упрощать, проверять и завершать работу без повторного согласования обычных обратимых действий. Не превращать пожелание в постоянный запрет, не добавлять новые требования от имени владельца.

Этот файл — единственная общая инструкция. `CLAUDE.md` и `START-HERE-RU.md` только направляют сюда. Документы с датами, старые очереди, issue и handoff — контекст; их назначения и запреты не возобновлять автоматически. Проверять текущий код и фактическое состояние задачи.

Один ответственный исполнитель доводит текущую задачу до результата. Дополнительный агент полезен только для конкретной независимой работы; отдельные роли, согласования специалистов и служебные issue не обязательны. Автоматическая «команда» из профилей и экспериментальных dispatch-workflow удалена. Не изображать запуск недоступных исполнителей.

## ПОСЛЕДНЕЕ РЕШЕНИЕ ВЛАДЕЛЬЦА 15.11.2026: Один этаж — до финального босса; объединить Пещеру

**Авторитетное ТЗ: [issue #314](https://github.com/w0980077002-create/territory-game-builde/issues/314), раздел «ОДИН ЭТАЖ = ОДИН ПОЛНЫЙ ЗАБЕГ С ФИНАЛЬНЫМ БОССОМ».** Игрок начинает этаж N; движется вправо, уничтожает волны, выбирает две развилки/портала внутри того же этажа, проходит последующие комнаты, побеждает **финального босса КАЖДОГО этажа**. **Только подтверждённая победа босса** завершает N и открывает следующий N+1 (в пределах существующих 100 этажей). Смена локации/волны, портал или обычный враг ничего не разблокируют. Поражение/выход не открывают новый этаж. Сохранить проверенный текущий арт, сцены, персонажей и босса; новые противники/боссы — ПОСЛЕ итогового теста владельца.

**Владелец явно разрешил РАЗРАБОТКУ объединения** уже принятой визуальной экспедиции с существующей серверной архитектурой в **одну** Пещеру. Это разрешение на код/тестирование на изолированной БД, **но не** на новые SQL/RPC/живые награды/новые списания/сброс в production. Старый черновик PR #522 не сливать целиком, PR #491 оставить до отдельного арт-этапа. Интеграция не равна скрытию вкладки; одна серверно подтверждаемая попытка должна охватывать весь этаж вплоть до босса. Играбельную безопасную тестовую версию проверяет владелец **в обычной TERRITORY через Telegram**. Исторический запрет «только отдельный прототип до разрешения» для этой конкретной Пещеры **уже пройден**, но gate безопасности реальных начислений остаётся. Не создавать второй режим, не терять восстановление начатых серверных сессий.

## Решение владельца 15.11.2026: Пещера — тестируем сейчас, cave-only сброс при релизе

**Прямое утверждение владельца:** Тёмную пещеру сейчас тестируют осведомлённые игроки. После окончания разработки и перед запуском окончательного режима **обнулить только тестовые этажи/попытки/прогресс/предметы/связанные с Пещерой ресурсы и достижения Пещеры**; прежние тестовые cave-состояния не надо переносить в финальный релиз. **Сейчас ничего не сбрасывать.** Перед финальной операцией определить реальные места хранения и сделать проверяемый избирательный план, не затронув общие аккаунты, золото, синие/красные алмазы, VIP, обычную экипировку, почту, профессии, Поход, Испытания и Арену. Cave-only сброс — отдельное разрешённое владельцем действие **на финальном этапе**, не автоматическая миграция и не право на общий wipe.

**Приёмка владельца — в обычной TERRITORY через Telegram.** Не требовать от него скачивать ZIP/артефакты/HTML с GitHub ради проверки; автоматические ролики — доказательство для разработчика, не замена настоящей игры. Тестовая Пещера остаётся изолированной от реальных наград до отдельного разрешения на выпуск. На боевом экране — чистовой UI без служебных «DEMO/ТЕСТ»; статус тестирования и отсутствие реальной добычи объяснять отдельно, без ложных обещаний. До финального релиза сохранять действующий cave-контракт и возможность завершить текущие тестовые сессии; **будущий cave-only сброс не означает вечного сохранения тестового прогресса**.

## Решение владельца 15.11.2026: GAMEPLAY FIRST → OWNER APPROVAL → SERVER

**ОБЯЗАТЕЛЬНЫЙ порядок для всех НОВЫХ игровых механик, боевых экранов, визуальной переработки и экспериментов.** Владелец напрямую требует: сначала увидеть настоящий играбельный результат на телефоне, поиграть, оценить визуал/геймплей, попросить переделать или удалить. **Только после его явного разрешения** переходить к серверной разработке. **Исключение по уже принятой Пещере: владелец дал разрешение на разработку и изолированные интеграционные тесты 15.11.2026; включение реальных выплат/сброса/новой схемы в production требует отдельного разрешения.** Предоставленная свобода выбора тестовых процентов и цен **не является** согласием на серверную интеграцию.

1. **A — изолированный локальный игровой вертикальный срез, не мёртвый макет:** показать настоящие анимации, действия кнопок, бои/победы/поражения, разбор/усиление, визуальные эффекты и осмысленный тестовый баланс. Клиентские тестовые состояния без реальных платных кошельков/настоящих наград; не маскировать их под live, но и не загромождать боевую сцену служебными ярлыками. Предоставить владельцу доступ к этой сцене **из привычной TERRITORY в Telegram**, а реальные кадры/запись использовать для проверки разработчика. Проверить 320/360/390/430px. Не называть это уже подключённым online-режимом.
2. **B — жёсткий gate владельца:** `нравится → интегрировать`, `переделать → повторить A`, `не нравится → удалить исключительно изолированный прототип`. Не считать «сборка зелёная» или отсутствие возражений согласием. Лишь владелец решает.
3. **C — сервер/сохранения/платежи для нового режима:** только после явного разрешения; использовать существующие аккаунты, проверенные квитанции, транзакции, идемпотентность, защиту от двойных наград и безопасный путь миграции. Это отдельный инженерный этап после утверждения GAME FEEL.
4. **КРИТИЧЕСКОЕ ИСКЛЮЧЕНИЕ:** в TERRITORY уже есть настоящие серверные этажи Пещеры и реальные сохранения. **Не отключать, не удалять и не ослаблять** их ВО ВРЕМЯ текущего тестирования; перед финальным запуском отдельно выполнить согласованный cave-only сброс без изменения общей экономики. Допустимо безопасно исправлять дефект существующей продакшен-системы, но **новую серверную интеграцию разрешено проектировать и тестировать только изолированно**; продакшен-активация не разрешена. Прототип тестировать изолированно; при отклонении удалять только его код/арт/тестовые данные, не игровую базу/кошельки/этажи.
5. **Для текущей задачи Codex по Пещере:** утверждена разработка **единого полного этажа до босса** на основе уже принятой живой сцены + существующего server-run/receipt/resume. Изолированная разработка/тесты кода, схемы и адаптера разрешены; новое server SQL, реальное списание, выдача live-наград и wipe в production **не утверждены**. Текущая задача подробно в [#314](https://github.com/w0980077002-create/territory-game-builde/issues/314); не запускать старый P0 заново и не сливать PR #522 целиком.

Этот порядок выше прежних «end-to-end» формулировок именно в части **времени серверной интеграции**, а не права стирать действующий backend. **Красивый играбельный результат → проверка владельца → отдельное разрешение серверу.**

## Что сохранять

- Одна работающая игра **TERRITORY**: React 18, Vite 5, TypeScript, Telegram WebView, Supabase. Продолжать существующую реализацию, не создавать вторую игру или дубли систем.
- Прогресс, валюты, VIP, предметы, экипировку и аккаунты игроков. Не сбрасывать общие данные, не проводить реальные платежи и не выдавать настоящие награды клиентским кодом. **Единственное согласованное исключение на будущее — точечное обнуление только тестового прогресса Пещеры перед её финальным запуском, НЕ СЕЙЧАС.** Не менять админский вход, секреты или баны заодно с UI.
- Серверные квитанции, идемпотентность, совместимость сохранений и защиту доступа. Не ослаблять проверки ради зелёного CI и не тестировать с записью в живые аккаунты.
- Утверждённый арт и игровые правила. Нужные для задачи требования — [GAME_REQUIREMENTS_RU.md](docs/GAME_REQUIREMENTS_RU.md); стиль — [ART_STYLE_LOCKED_TERRITORY_V1_20261027_RU.md](docs/ART_STYLE_LOCKED_TERRITORY_V1_20261027_RU.md). Не читать всю историю проекта перед каждой небольшой правкой.

Общее техническое управление не означает сброс живой базы, смену экономики или массовую рассылку. Изменение production должно быть необходимо конкретной задаче, сохранять данные и иметь проверенный план перехода и отката. Сначала подготовить и проверить реализацию; отдельный опасный шаг не останавливает независимые безопасные части работы. Сообщения игрокам отправлять только по поручению на конкретную публикацию.

## Порядок работы

1. Проверить `git status`, ветку и актуальный код. Сохранять чужие изменения. Если работа идёт в GitHub, сверить свежий `main` и пересекающиеся PR.
2. Исправить причину и закончить один проверяемый сценарий. Не расширять задачу инфраструктурой, переписыванием рабочих режимов или дополнительными отчётами без необходимости. Для связного изменения использовать ветку и PR; локальные обратимые правки можно коммитить без отдельного разрешения.
3. Выполнить `npm run typecheck`, `npm run lint`, `npm run build` и относящиеся к изменению тесты из `package.json`. Не удалять падающие тесты и не менять их ожидания только ради прохождения. Повторять проверки при новых изменениях или обнаруженной проблеме.
4. При изменении интерфейса пройти путь игрока, проверить узкий экран и RU/EN; для Пещеры — 320/360/390/430 px и малую высоту. Проверку Chromium не называть проверкой физического телефона или Telegram WebView.
5. Проверенную безопасную работу завершать самостоятельно, **но новые игровые механики и редизайн до личной приёмки владельца — только изолированное превью/PR**; не сливать и не публиковать непринятый прототип. Не сливать незавершённый/красный PR и не включать auto-merge. Сначала PR, проверки и личная приёмка **в Telegram**; затем отдельно разрешённый финальный серверный выпуск. Уже существующий изолированный путь тестовой Пещеры в TERRITORY не заменять загрузкой GitHub-артефакта.
6. Единственная публикация игры — `.github/workflows/pages.yml`, `main`, GitHub Pages. После выпуска проверить workflow и опубликованный SHA (`node scripts/check-published-pages.mjs`). Vercel в этом проекте не используется.
7. Коротко сообщить по-русски: результат, проверки, где увидеть, что не проверено. Issue, план, PR и локальная сборка сами по себе не означают выпуск.
