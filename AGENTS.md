# TERRITORY — единые рабочие правила

> Обновлено 16.11.2026 после проверки актуального main, релиза #541 и действующих GitHub Actions. Это инструкция исполнителю, а не новая очередь задач. **Последнее прямое поручение владельца важнее этого файла.**

## 1. Самостоятельность без бюрократии

- Работать над **последней реально порученной задачей**, сверяя код, свежий main, историю relevant PR и фактическую публикацию. Не запускать старые ТЗ, очереди, handoff, роли и запреты из архивных документов как новые задания. Не заставлять владельца повторять уже принятое решение.
- Codex и Claude работают **в одной TERRITORY по очереди**; один ответственный завершает задачу. Второй допустим как помощник для независимой непересекающейся работы, без соревнования, отдельных игр или дублирующих PR. Не обещать фоновую работу без реального запуска.
- Для согласованных исправлений, клиентского UI, арта, анимаций, текстов и безопасных обратимых улучшений: изучить проблему → изменить → проверить → самостоятельно довести до main и GitHub Pages, если тесты зелёные, дифф безопасен и нет конфликтов. **Не требовать отдельного разрешения на каждый merge, выпуск, ревью, видео или «личную приёмку ДО публикации».** Владелец оценивает итог прямо в Telegram и вправе потребовать доработку или откат.
- Для **новой, ещё не утверждённой механики или радикальной смены геймдизайна** сначала честный играбельный изолированный вариант внутри обычной TERRITORY для оценки владельца, без реальных наград/платежей/нового live-backend. Одобрение механики не означает разрешения на рискованные действия с данными.
- Не превращать полезные локальные тесты и артефакты CI в обязательные ручные церемонии. Issue/PR нужны для реального объёма и проверки; не открывать отдельные служебные issue и не писать многостраничные отчёты ради самого процесса. Никаких фиктивных «всегда работающих агентов».

## 2. Единственные действительно опасные операции

**Отдельно согласовывать конкретный необратимый или экономически опасный шаг**, а не всю безопасную задачу: применение нового production SQL/Edge/серверной схемы; массовый reset/migration, изменение ownership или сохранений; реальные выплаты, изменение платёжных и премиальных кошельков, VIP и экономики; массовые публикации игрокам; секреты/авторизацию/критические политики доступа; дополнительные платные сервисы.

- Существующий прогресс, предметы, алмазы, золото, VIP, профессии, Arena/Поход/Испытания, история квитанций и данные игроков неприкосновенны. Не обходить идемпотентность, серверную проверку владения, RLS, ограничения по наградам и защиту от дубликатов.
- Исключение на будущее: владелец одобрил **точечный сброс только тестовых данных Пещеры непосредственно перед окончательным запуском Пещеры**. **СЕЙЧАС СБРОС ЗАПРЕЩЁН.** Перед ним — карта реального хранения, проверка изоляции и отдельное разрешение на конкретное действие. Никакого общего wipe.
- Для нового режима или серверного расширения сначала игровая проверка, затем изолированные интеграционные тесты и только после отдельного решения — production. Разрешено исправлять доказанный дефект уже действующей системы безопасной, проверенной обратимой правкой; не переписывать сервер без необходимости.
- Платежи, выдачи игрокам, новости и администрация — только в пределах конкретного поручения. Не делать опасный шаг незаметно под видом «полировки».

## Утверждённая граница Supabase · 16.11.2026

Владелец утвердил: **Supabase только для необходимой авторизации, серверных сохранений/прогресса, кошельков (золото, алмазы, VIP), инвентаря/экипировки/кузницы/профессий, PvP Арены и рейтингов, аукциона/торговли/платежей, проверенных наград и квитанций**. В Пещере через сервер идут только необходимые status/start/finish, камни, глубина, история и защищённые подтверждения. **Обычный PvE-бой, движение, удары, анимации, VFX и камера исполняются локально на телефоне.** Не добавлять серверный combat tick, дополнительные SQL/Edge/таблицы для косметики и кадров. Устаревшие тестовые системы и резервные таблицы удалять только после проверки отсутствия активных обращений, recovery-потребителей и наличия нужных бэкапов; исторические миграции не удалять. Не отключать RLS, CAS, защиту экономических операций и действующие cron-режимы.

## 3. Действующая Пещера — не создавать снова

- **Объединение уже выполнено:** PR #533 merged. **Анимации и визуальные эффекты из VIKING уже в main:** PR #541 merged 16.11.2026. Issue #540 реализован как визуальный этап. Не ставить их вновь как невыполненные задачи. Прежние #491 (транспорт арта) и #522 (устаревший серверный combat) не использовать для merge/cherry-pick целиком.
- Один вход в Тёмную пещеру, одна живая CaveExpeditionPreview, без переключателя двух Пещер. Бой, движение, удары, четыре участка/порталы, фазы босса и клиентский checkpoint работают на телефоне, **не через серверный combat tick**. Существующие серверные операции ограничены прогрессом/камнями и необходимым безопасным legacy-recovery. Проверять реальный код, не переоткрывать завершённое объединение.
- 100 этажей; полный этаж заканчивается **победой финального трёхфазного босса**, а не обычным противником/комнатой. Можно перепроходить любой завершённый этаж ради обычного floor-specific лута без изменения максимальной глубины; новая честная попытка — по прежним правилам камней и наград, повтор одной квитанции не начисляет повторный приз. Не менять действующие формулы или контракты под видом UI.
- Не внедрять автоматически реальную ценную добычу, премиальные начисления или новые серверные действия из клиентского результата. Сохранять recovery старых сессий и общий прогресс. Полный контракт: https://github.com/w0980077002-create/territory-game-builde/issues/314 и docs/CAVE_UNIFIED_RELEASE_20261115_RU.md.
- Утверждённые арты/герои/спутники/предметы, 7 зелий, экипировка и остальные режимы не подменять чужими. Пещерные движения/VFX не должны изменять урон, RNG, drop, HP, фазу, сервер и баланс. Кандидатов из VIKING распределять по утверждённым режимам, не переносить всех 21 автоматически. Отбракованную Балерину не возвращать.

## 4. Изменение → проверка → видимый результат

1. Сверить актуальные main, затронутые файлы, пересекающиеся PR, границы задачи и отсутствие правок чужих режимов. Не откатывать чужую работу и не переписывать работающие подсистемы. Если задача уже завершена — исправлять только подтверждённый остаточный дефект.
2. Делать один законченный проверяемый вертикальный результат. BE AMBITIOUS означает качество существующего, а не создание новых систем. Не добавлять несогласованные условия, сроки, проценты, роли или новые разрешительные этапы.
3. Минимум: npm run typecheck, npm run lint, npm run build и **относящиеся к задаче** тесты из package.json. Сохранить реальные регрессии: не удалять падающие тесты и не переписывать assert для зелёной галочки. Рискованные сценарии проверять изолированно, без записи в production.
4. Для UI — путь реального игрока, RU/EN и узкие телефоны; для Пещеры 320/360/390/430 px, низкие высоты, пауза/скорость/reload/выход/возврат. Браузерный Chromium — не физический Telegram WebView. Если мобильный WebView не проверялся, так и писать.
5. Проверенная одобренная безопасная работа: PR при необходимости → проверка **финального SHA** → merge → единственный Pages workflow в main → проверка workflow и опубликованного SHA. Не держать PR draft лишь ради просмотра владельцем уже одобренного визуала; не сливать красный, незавершённый или конфликтующий PR. Auto-merge не включать без поручения.
6. Отчитаться коротко: что реально изменено, SHA/PR, статус CI/Pages, что можно увидеть в Telegram и какие риски/проверки остаются. Не называть код в PR опубликованным, а облачный тест — реальной телефонной проверкой.
