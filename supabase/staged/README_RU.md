# Неприменённые серверные изменения TERRITORY

Эти файлы — **проект серверных миграций, не готовый для непосредственного применения на рабочей БД**:

- `territory_stage3_backend.sql`: защищённые таблицы/функции крафта, авторитетного кошелька, 25 камней/день и сезонных очков; флаги всех операций выключены. Не заменяет полный перенос сохранений.
- `territory_stage3_pvp_normalize.sql`: изменение сервера Арены для игроков и ботов; необходима отдельная тестовая проверка режимов 1x1 / 3x3 / Хаос.
- `territory_craft_catalog.json`: снимок 17 рецептов из действующего `src/game/professions.ts`. Тест `scripts/check-stage3.mjs` предупреждает о расхождении.

НЕ переносить эти SQL в migrations и НЕ применять в рабочем Supabase без резервной копии, отдельной проверки и подтверждения владельца. Особенно важно: существующий `players.game_state` остаётся клиентским, поэтому новая серверная инфраструктура сама по себе не закрывает накрутку.

## Этап 8: защищённые профессии (проект, выключен)

`territory_profession_stage8_backend.sql` — отдельная серверная модель для **72 рецептов** из `territory_profession_stage8_catalog.json` (55 новых и 17 исходных). Она **требует** ранее проверенные таблицы Stage3, ничего не запускает автоматически и создаёт флаг `territory_profession_stage8_release.enabled=false`. После изменения модели выполнить `node scripts/professions/export-stage8.mjs` и `npm run sync:professions:stage8:sql`, затем тест полной JSON↔SQL идентичности.

- `territory_profession_stage8_status()` возвращает `enabled=false` до включения и для несверенного аккаунта; не выдаёт авторитетных балансов из клиентского сохранения.
- `territory_profession_stage8_execute(recipe,operation_id)` списывает только серверные ресурсы; блокировка игрока/кошелька, суточный лимит 300 XP по Киеву, квитанция повторного запроса, проверка профессии/уровня/лицензии.
- `territory_profession_stage8_inventory()` возвращает серверно подтверждённые изготовленные вещи после перезахода с другого устройства, исключая просроченные зелья. Это только безопасное **чтение**: экипировку, расходование и торговлю ещё нужно защищать отдельно.
- `practice` начисляет опыт без предмета. `item` создаёт уникальную серверную вещь; 7 суток действуют на созданные зелья и эликсиры, но **не** на добытые ресурсы.
- Новая шкала XP несовместима со старой. Поэтому используется отдельная `territory_profession_stage8_progress`, старые `territory_profession_mastery_v1` и `players.game_state` не переписываются. `territory_profession_stage8_reconcile(player_id)` разрешён только `service_role` после проверки старого серверного состояния; сохраняет уровень, долю XP и снимок прежнего прогресса.
- `territory_profession_stage8_purchase(profession,operation_id)` — атомарная покупка новой профессии: сервер списывает 1000 синих алмазов, создаёт unlock, Stage8 lvl1 и квитанцию; повтор того же UUID не списывает повторно. Требуются `players.created_at >= release.cutover_at`, отсутствие старых unlock/mastery и уже закрытый прямой UPDATE для `players.gems`.
- `territory_profession_stage8_initialize()` допускает и альтернативную *доверенную* покупку, если service_role заранее записал immutable `new_unlock_events`. Он не превращает старого игрока без записи v1 в «новичка».
- Флаг `enabled=true` требует `cutover_at`; Stage8 отклоняет операции, если `authenticated` может напрямую менять валюту, ресурсы, unlocks или вызывать старый RPC покупки. Сначала завершить единый экономический cutover.

**Нельзя** включать stage8 на реальных игроках до удаления client-local crafting, защищённой сверки прогресса, тестов двух устройств/повторов/DST/RLS, резервной копии и отдельного разрешения владельца.

### Аудит фактической базы и перенос существующих профессий (25.10.2026)

Read-only сверка production обнаружила 89 аккаунтов, 13 серверных открытий профессии и 13/13 совпадений с сохранённым выбором. Только 5 аккаунтов имеют уровень профессии выше первого; максимальный — 6. Это небольшой объём для осторожной сверки, **не** доказательство достоверности клиентского XP. В `public` нет `territory_profession_mastery_v1`; Stage8 backend поэтому нельзя непосредственно применить на рабочей базе без отдельного плана зависимостей.

`territory_profession_stage8_legacy_bridge.sql` — вариант для **проверенной вручную** записи старых уровней в отдельную таблицу Stage8. Приватный `legacy_preview(player)` отдаёт проверяемый снимок только service_role. `legacy_approve(player,digest,note)` требует идентичный серверный unlock, совпадающую профессию, корректные дробные XP, совпадение ревизии и явное описание проверки; результат однократен и не меняет `players.game_state`, валюту, экипировку. Происхождение помечается `reviewed_legacy_save`, никогда `verified_v1`: это сохранённый клиентом уровень, а не доказанное сервером ремесло. Автоматическая массовая выдача доверенного статуса запрещена.

`territory_stage8_save_cutover.sql` добавляет только ограниченный серверный CAS для косметических настроек, с защитой от повторов и чужих аккаунтов. Отдельная service-role проверка `territory_stage8_save_cutover_preflight()` перечисляет запрещённые прямые права и несуществующие пока доверенные серверные обработчики наград за PvE/задания/достижения/использование предметов. Предохранитель намеренно **всегда красный**, пока не создана и проверена полная серверная экономика; подмена названий RPC и снятие прав наугад не считается исправлением. Офлайн-проверка: `node scripts/check-stage8-save-cutover.mjs`.

**Обнаруженный стоп перед живым подключением:** роль `authenticated` в рабочей базе до сих пор имеет `UPDATE` на столбцы `players.game_state` и `players.gems`; старый RPC `territory_profession_unlock(text)` доступен. При этом `players.game_state` записывается клиентом, а guard проверяет согласованность полей, а не происхождение награды. Новый Stage8 намеренно отвечает `economy_not_server_authoritative` и оставляет игру в старом режиме. Простое включение флага, удаление старых grants или объединение PR с `main` без защищённого серверного пути всех игровых начислений недопустимо: первая мера не закрывает накрутку, вторая сломает сохранения игроков.

Также перед любым реальным развёртыванием необходимо сверить **фактический Supabase project ref из опубликованного Telegram/GitHub Pages клиента** с выбранной базой: одноимённые проекты могут содержать разные таблицы. Stage8 требует существования проверенных `territory_resource_wallet`, `territory_profession_unlocks`, `territory_profession_mastery_v1`; отсутствие любой таблицы — жёсткий стоп, а не повод создать пустую копию или автоматически импортировать клиентский `game_state`.

Проверка **25.10.2026** (только чтение): публичный JS на GitHub Pages содержит endpoint `wmyrdpbwlkzsktnhookx.supabase.co` (проект `bolt-native-database-71669285`). У отдельного проекта `territory-game-builde` (`ksikzkrvuuhermhnbycn`) таблиц `public.territory_resource_wallet`/`public.territory_profession_unlocks` нет. Это подтверждение текущей сборки, а не разрешение менять legacy-БД. Перед выпуском проверить опубликованную сборку заново. В доступных проектах нет подтверждённого отдельного стенда для безопасного удалённого тестирования; текущие интеграционные тесты идут в локальном PGLite.

### Фактический LIVE для пакета кланы/сезоны/слоты/аукцион (26.10.2026)

В `.github/workflows/pages.yml` у действующей сборки явно указан **`wmyrdpbwlkzsktnhookx`**, а **не** одноимённый, но независимый `ksikzkrvuuhermhnbycn`. Проверка SQL ниже была только чтением системного каталога и настроек, без изменения данных игроков:

| Модуль | Состояние в `wmyrdpbwlkzsktnhookx` | Разрешённый следующий шаг |
| --- | --- | --- |
| Кланы | Таблицы и RPC не установлены; защищённый кошелёк лицензии мастера существует | Сверка полного `territory_stage1_clans_install.sql` в отдельной тестовой PostgreSQL-копии, затем reviewed установка |
| Слоты | Hall account/session и квитанции есть; `territory_slots_v1` отсутствует | Проверить реальную конкурентность, установить SQL **выключенным**, протестировать и лишь затем отдельно включить |
| Недельные сезоны | RPC и таблицы присутствуют, но `enabled=false`, `prizes=[]`, cron job отсутствует | Не повторять установку вслепую; сверить существующие определения, применить только проверенный diff функции `weekly_season_tick_v1`, затем cron и призы |
| Аукцион | Нет `territory_wallet_v1`, `territory_crafted_items_v1`, `territory_release_flags_v1` | **Не устанавливать** Stage5: требуется серверный cutover крафта/кошелька с проверкой старых предметов и сохранений |

В текущем LIVE `weekly_season_tick_v1` ещё не содержит исправление на пустое отображаемое имя и nullable `banned` из `docs/WEEKLY_SEASONS_RELEASE_RU.md`. Действующие профили сейчас не имеют этих двух аномалий, но любой будущий профиль может прервать закрытие всей недели. Перед включением наград нужен именно проверенный diff. Локальные PGlite-тесты и GitHub CI не заменяют remote PostgreSQL staging, проверку резервной копии, Telegram WebView и отдельное согласование высокорискового выпуска.
