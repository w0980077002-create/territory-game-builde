# TERRITORY — STAGE5: защита сохранений и подготовка серверного аукциона

**База обновления:** GitHub `main` `55581583938925b14aaab08312d29e28f6e04247` (STAGE4). Архив содержит **полный проект**, а не патч: в существующем `.github/workflows/unpack-project.yml` синхронизация файлов выполняется с `rsync --delete`. Загружайте обе части `TERRITORY_STAGE5_FULL.zip.part01` и `.part02` в корень `main` одним коммитом. ZIP внутри разделён на два последовательных бинарных куска; распаковывать куски отдельно нельзя.

## Исправления, реально применяемые после распаковки исходников

1. **Осторожные облачные сохранения.** Перед записью полного `game_state` браузер сравнивает значение `players.updated_at`, полученное при загрузке или успешном сохранении. Если другое окно обновило строку, старое окно НЕ перезаписывает новые данные и блокирует последующие слепые попытки. Когда соединение/сохранение не подтверждено, интерфейс показывает красное предупреждение. Данные из старого сохранения продолжают мигрироваться без сброса VIP, экипировки, камней, алмазов, профессий, почты и этажей. Этот механизм **не защищает от злонамеренного клиента** и не является истинной блокировкой экономики.
2. **Настоящий серверный формат аукциона, но пока без торгов.** Экран подгружает только подтверждённые сервером экземпляры товаров мастеров из RPC. Не создаёт фиктивные лоты, не выдаёт локальных наград и не подменяет `game_state`. Показывает серверный остаток золота и допускает выставление, покупку или отмену только когда сервер явно включил функцию. При сетевом сбое позволяет повторить действие **с тем же ID**, чтобы не продублировать операцию. Чат прежний и **не верифицирует отправителя**, поэтому ему нельзя доверять как подтверждению сделки.
3. **SQL серверного аукциона в `supabase/staged/territory_stage5_auction.sql`.** Верифицированные кошельки и серверно-созданные уникальные предметы, блокировка предмета на время продажи, атомарная передача предмета и золота, запрет покупки собственных вещей, 10% комиссии на серверный казначейский счёт, проверка цен/остатков, журнал операций с повторными UUID, RLS и отсутствие прямых прав клиентов на кошельки/лоты. Все новые функции имеют `auction_enabled = false` по умолчанию. SQL **не накатывается автоматически**, а ожидает безопасного перехода экономики на сервер.
4. **Регрессии Stage5.** `npm run test:stage5`; команда `npm run test:economy` теперь включает тесты нового этапа. В `pages.yml` оставлен прежний контрольный `economy-release.json`.

## Серьёзная проблема живой экономики НЕ исправлена

15 октября 2026 read-only аудит подключённой Supabase (`wmyrdpbwlkzsktnhookx`) показал 41 игрока и что роль `authenticated` может изменять `public.players.game_state`, `gems`, `gold`, `level`, `updated_at`. RLS `update_own_player` запрещает трогать **чужую** строку, но разрешает подделывать собственные алмазы, золото, экипировку и прогресс. Следовательно, **экономика сейчас не имеет настоящей серверной защиты.**

Ни один браузерный фикс этого не исправит. Перед отзывом `INSERT/UPDATE` с `players` потребуются: инвентаризация всех игровых записей/действий; доверенные серверные операции с лимитами и проверкой телеграм-личности, анти-replay и идемпотентностью; отдельные официальные источники золота, алмазов, предметов, лицензий, VIP; сверка старых кошельков/прогресса с документированным происхождением и снимок БД; тесты конкуренции и обратной совместимости; только затем перенос записи и `REVOKE`. Преждевременный `REVOKE` лишит игроков возможности сохранять игру.

Файл `economy-release.json` оставлен с `ready: false` — **публикация новых сборок на GitHub Pages заблокирована до настоящего безопасного cutover**. Это сознательная мера; распаковка ZIP и прохождение CI не означают публикацию. Не включайте `ready: true` ради ускорения.

## Проверка

- `npm run test:professions`, `test:feature-separation`, `test:mobile-home`, `test:progression`, `test:stage3`, `test:stage4`, `test:stage5`: пройдено локально с установленным глобальным TypeScript.
- По коду: синтаксис TS/TSX проверен тестом Stage4; Stale-save проверен моделированием двух устройств и idempotency — модульным тестом Stage5.
- **Не проверено:** реальное применение Stage5 SQL на изолированной Postgres/Supabase и интеграционные гонки; живую базу не изменяли. `npm ci`/полная `vite build` локально не выполнены, потому что в изолированной среде отсутствует npm-пакет и сеть; GitHub CI после загрузки выполняет `npm ci`, `typecheck`, тесты и `build`.
- Не тестировались денежные начисления и покупки; сезонные награды и платные лицензии остаются выключены до серверной валидации.

## Что не делать

Не запускать `supabase/staged/territory_stage5_auction.sql` в боевой БД независимо от загрузки ZIP. Не трогать аккаунты игроков, VIP, личные алмазы, золото и предметы во время упаковки. Не выдавать показательные награды/лоты из старого локального `game_state`. Не отключать GitHub Pages защитный gate вручную.
