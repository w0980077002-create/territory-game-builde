# TERRITORY — Пакет 3: честный сезонный рейтинг, подготовка серверной экономики и PvP

Исходный коммит main: `8db6a18317f68c33c0e0642d5e83b5b52b57d673` (пакет 2).
Установка: один **полный архив проекта**, поделённый на `TERRITORY_STAGE3_FULL.zip.part01` и `TERRITORY_STAGE3_FULL.zip.part02`, для существующей GitHub-автораспаковки. Не загружать один ZIP одновременно с частями.

## Действующие изменения (без миграции базы)

1. В **Топ игроков → Сезоны** появился отдельный экран недельного чемпионата (RU/EN). Таймер считает настоящую неделю по киевскому времени, с переходом зимнего/летнего времени. Включение чемпионата **не имитируется** — до серверного запуска виден статус «Подготовка», призы НЕ начисляются.
2. Экран умеет отображать **реальный, подтверждённый сервером** сезонный топ после будущего включения специально защищённого RPC `territory_season_status_v1`. Пока этого RPC нет, нет и поддельных очков.
3. Рейтинг **«По победам»** теперь запрашивает 50 игроков, действительно отсортированных базой по числу побед на Арене. Раньше среди 50 игроков с наивысшим рейтингом сортировались только их победы; сильные по количеству побед игроки могли не попасть в список. Быстрое переключение вкладок больше не даёт старому сетевому ответу перерисовать текущую вкладку.
4. Награды от администратора в почте: повторные быстрые нажатия в одной вкладке не отправляют одинаковые запросы одновременно. При временном сбое серверного подтверждения письмо не пропадает из списка вручную до следующего обновления.
5. Добавлены регрессионные проверки календаря, DST, PvP-бюджетов, сезонной инфраструктуры, серверных рецептов, стонового лимита, лидерборда и TS/TSX-синтаксиса.

## Подготовленный серверный фундамент (НЕ активирован)

SQL хранится в `supabase/staged/` — **не** в каталоге автоматически запускаемых миграций. Базу Supabase мы сознательно не меняли.

- **17 серверных рецептов** с ингредиентами и предметами, совпадающими с клиентским каталогом. Атомарное списание из настоящего `territory_resource_wallet`, уникальная серверная копия предмета, серверное мастерство и квитанция с `operation_id` для корректного повтора без двойного крафта. Состояние профессии должно быть проверено при переносе существующих игроков, без сбросов.
- **Серверная покупка камней**: цены 2 синих алмаза за 1 камень или 8 за 5; максимум 25 купленных камней в сутки по Киеву, с атомарным списанием, единственным серверным кошельком, строгими границами и idempotent-квитанцией.
- **Сезоны**: серверные события с уникальным источником награды, дневными лимитами по категориям, серверной датой воскресенья в Киеве, начисление разрешено только `service_role` после подтверждения реального события. RPC таблицы лидеров — только для чтения. Запуск соревнования и начисления по умолчанию выключены.
- **Арена**: подготовлено нормирование стартовых характеристик живых игроков и ботов. Бонус уровня не более 3%, влияние неподтверждённых характеристик экипировки — не более 2%; персонаж с 81-м уровнем и необычайной атакой перестаёт убивать новичка одним ударом *после отдельного внедрения SQL*. Эликсиры во время боя по-прежнему дают обычные временные эффекты. Правила PvE вообще не меняются. Существующие открытые комнаты остаются нетронутыми.

**Это не «защита экономики завершена».** На нынешней базе клиенты могут записывать собственные `game_state` и `gems`; покупка камней, крафт и сезонные очки пока не используют новый серверный протокол. Подмена игрового состояния через прямой Supabase API всё ещё возможна. Нельзя выдавать staged SQL за развернутую защиту.

## Что обязательно сделать перед переключением рабочей базы

1. Сделать резервную копию рабочей БД, проверить авторизацию Telegram и админские выдачи, все действующие кошельки и профессии. Не удалять данные тестеров.
2. На отдельной тестовой БД прогнать параллельные транзакции покупки/крафта/наград, падение сети после коммита, повтор `operation_id`, попытку выбрать другую профессию, спорные старые уровни мастерства. Одна локальная SQL-фикстура не доказывает защиту сети.
3. Сверить серверное состояние с персонажами на рабочей базе; **не доверять** безусловно данным `game_state` от браузера. Согласовать спорные или накрученные старые накопления с владельцем отдельно.
4. Перевести клиент с `saveCloudSave` и локального `craftItem` на действия с уникальными квитанциями, добавить в сервер валидаторы всех источников монет/алмазов/XP/предметов (Поход, Испытания, Арена, квесты, бонусы, админка, магазин). Прямые UPDATE/INSERT в защищённые колонки затем закрыть на SQL-уровне. Без этого серверная экономика остаётся незавершённой.
5. Проверить нормирование PvP с игроками разного уровня, ботами и эликсирами, и отдельно дать разрешение на SQL-выкатку/начало сезонных наград. Не включать реальные платежи и аукцион до аудита транзакций.

## Проверки

`npm run test:stage3`, `npm run test:stage2`, `npm run test:balance`, `npm run test:professions`, `npm run test:feature-separation`, `npm run test:mobile-home`, `npm run test:client-guard`, тесты Telegram.

GitHub Actions после загрузки полного ZIP дополнительно сделает `npm ci`, `npm run typecheck`, `npm run test:economy` (теперь включающий тесты stage3), остальные проверки и `npm run build`. Успешная сборка **не равна** публикации: workflow `pages.yml` защищён gate `economy-release.json.ready=false`. Для публикации сборки служит действующий `Territory - publish working game (restore Pages)`.

Персонажи, деньги, камни, VIP, этажи, аукцион, существующие чаты и база **не сбрасываются и не модифицируются**.
