# TERRITORY 1.0 — пакет аукциона T9–T12

Изменения подготовлены локально, SQL находится только в `supabase/staged/territory_v1_auction_completion.sql` (однократный сценарий, повторное применение запрещено конфликтующими DDL и откатывается целиком). Production не изменён, публикация и флаги не включены. Пакет содержит серверные операции T9–T12 и контракт для визуальных экранов, но не означает production-релиз.

## Реализовано

- Расширены существующие таблицы Stage5, без второй копии предметов или кошельков. Золото/синие алмазы используют проверенный `territory_wallet_v1`, красные — действующий `territory_master_license_red_wallet_v1`. Никакого импорта суммы из редактируемого `game_state`. Сделка сверяет, блокирует и обновляет основные `players.gold/gems` и JSON-проекции вместе с каноническими кошельками; старое сохранение клиента не может вернуть прежний баланс. При выключенном флаге все прежние записи остаются прежними. При включённом флаге доверенные серверные обработчики почты/Арены/рефералов синхронизируют кошельки по проверенному old/new, а прямое изменение валют клиентом отклоняется. Идентичность обработчика определяется `current_user` в SECURITY INVOKER-триггере, а не клиентским полем или GUC.
- `territory_auction_trade_v2`: `list/buy/cancel`, валюта `gold/gems/redGems`, положительная цена, шаг 10 для обоих алмазов, срок 1–86400 секунд; срок лота ограничен оставшимся сроком предмета. Комиссия `ceil(price/10)` соответствует прежнему серверу. Нет новых цен.
- Блокировки экземпляра, лота, кошельков, повторные UUID с неизменными аргументами, запрет собственной покупки, атомарные дебет/кредит/комиссия/передача. При истечении возвращается `outcome: expired`, а деньги не списываются. Клиент обязан отображать outcome, а не считать любой `success` покупкой.
- Проверенные ресурсы продаются из того же `territory_resource_wallet`: сервисная сверка `territory_auction_reconcile_resources_v1` добавляет партии с подтверждёнными исходными датами и provenance, только если их сумма в точности равна существующему агрегату. Это не операция выдачи. Размещение вычитает количество из агрегата в escrow; покупка/возврат восстанавливают исходные даты партий. Триггер существующего кошелька заставляет текущие craft/gather-операции тратить oldest-expiring-first и исключать истёкшее. Новое серверное начисление получает существующий семидневный срок. Непроверенные исторические агрегаты не продаются.
- Stage3 и Stage8 предметы передаются сменой владельца действительного экземпляра. Камни, связанные с ID экземпляра, сохраняются. Триггеры БД запрещают удаление/изменение вещи в escrow, фактическое сохранение экипировки с выставленным или уже проданным ID отклоняется. Stage8-инвентарь не возвращает escrow-вещи.
- Истёкший лот освобождает escrow без комиссии; повторное выставление создаёт новый лот. Частная `territory_auction_expire_v2` идемпотентна, использует `SKIP LOCKED`, вызывается при обзоре и размещении. Служебная функция для расписания подготовлена: его включение требует отдельного релиза.
- Поиск по исходному/собственному имени, мастеру и продавцу; категории, редкость, валюта, цена и ближайший срок. История использует снимок товара на момент размещения.
- Новые произведённые экземпляры получают неизменяемые ID/имя изготовителя. Старые товары не приписываются текущему владельцу. Новые материалы/расходники получают существующий семидневный срок; исторические данные без срока не переписываются.
- `territory_auction_name_item_v1`: проверенная профессия 300 (не уровень героя), купленная лицензия с квитанцией, собственный изготовленный невыставленный предмет, длина 1–60 символов. Сохраняется `customName`, исходный шаблон и характеристики не меняются; при перепродаже имя и изготовитель сохраняются.
- `src/game/auctionCompletion.ts`: типы (включая `source: resource`), API, проверка ответов, таймауты, сохранение ожидающей операции отдельно для аккаунта; сравнение характеристик сопоставимых по слоту/уровню/редкости мастерских и добытых вещей. Множители баланса не назначаются автоматически.
- Старые RPC адаптированы к золоту Stage3 и не могут обходить новые проверки или случайно тратить алмазы. Квитанции старого формата продолжают возвращаться при повторении прежнего запроса.

## Интеграционный контракт для ChatGPT

```ts
import {
  fetchAuctionCompletion, keepPendingAuctionCompletion,
  readPendingAuctionCompletion, submitAuctionCompletion,
} from '../game/auctionCompletion';

const overview = await fetchAuctionCompletion({ currency: 'gems', category: 'equipment' });
const operation = { id: crypto.randomUUID(), action: {
  action: 'list' as const, itemId, source: 'stage8' as const,
  price: userEnteredPrice, currency: 'gems' as const, durationSeconds: 86400,
} };
await keepPendingAuctionCompletion(operation);
const receipt = await submitAuctionCompletion(operation.action, operation.id);
// Показывать receipt.outcome; после подтверждённого ответа удалить ожидающую операцию.
await keepPendingAuctionCompletion(null);
// После обрыва связи: readPendingAuctionCompletion(), повторить те же action и id.
```

Карточки/переключатели/экраны исполнителя ChatGPT не изменены. Для ресурсов применяется тот же `submitAuctionCompletion`, с действием `{ action: 'list', source: 'resource', resourceId: 'gather-ore', quantity, price, currency, durationSeconds }`; `overview.resources` показывает доступное число с учётом живых партий после сверки. Поле `source` у лота различает Stage3/Stage8/ресурсы.

После мутации нужно перечитать серверный обзор и авторитетное сохранение. API не начисляет валюты в клиентское состояние.

## Проверки

- `node scripts/check-v1-auction-sql.mjs`: реальное выполнение PostgreSQL в PGlite; три аккаунта, три валюты, шаг, сохранение сумм с комиссией, повторные UUID/другие аргументы, второй покупатель, отказ при недостатке денег, истечение/возврат/перевыставление/отмена, поиск, уровень профессии, квитанция лицензии, неизменность мастера и характеристик, реальное запрещённое удаление/recycle и equip-save, сверка и передача партий ресурсов, расход старых партий существующим craft UPDATE, положительный gather UPDATE, зеркала кошельков, доверенная выплата, отклонение клиентского сохранения и невозможность SET ROLE service_role из настоящей authenticated-сессии, ACL.
- `node scripts/check-v1-auction-client.mjs`: локальные RPC-моки, неверные параметры/ответы, исход `expired`, долговечная операция по аккаунту, сравнение предметов. Сеть и production не используются.
- `npm run typecheck`: пройдено при сдаче пакета; повторяется общим исполнителем после интеграции.

## Ограничения перед релизом

1. Сначала установить на изолированной БД проверенные Stage3, Stage5, Stage8 и схемы магазина лицензии; затем этот сценарий, один раз. Оба `auction_enabled` и `auction_completion_enabled` должны оставаться выключенными до приёмки.
2. `territory_resource_wallet` исторически содержит агрегаты без партий/сроков. Для каждого игрока/ресурса оператор должен передать проверенные исходные партии в сервисную `territory_auction_reconcile_resources_v1`. API проверяет точное равенство сумм и не изменяет существующее количество. До такой сверки ресурсы остаются в старой игре, но продажа через новый аукцион отклоняется. Данные клиентов не являются доказательством; нельзя приписывать старому запасу новый семидневный срок. Покупателю также нужна сверка ресурса (в том числе пустого остатка); иначе покупка отклоняется атомарно. До продажи сервер проверяет отсутствие прямых INSERT/UPDATE/DELETE клиента для ресурсного кошелька.
3. Перед активацией визуальные экраны должны использовать новый контракт и обновлять серверный инвентарь после сделок. БД уже запрещает delete/update вещей в escrow и equip-save неверного владельца, Stage8-инвентарь фильтрует escrow. Полноценное использование/переработка любых старых локальных предметов по-прежнему требует общего авторитетного cutover; клиентский снимок не является доказательством владения.
4. До ввода нужен общий cutover проверенных кошельков, сохранений и owned-инвентаря, включая отражение серверных сделок в основном сохранении. Этот пакет не меняет grants существующих сохранений. После включения флага прямые изменения валют клиентом блокируются, серверные подтверждённые выплаты поддерживаются, поэтому до активации все клиентские источники валют должны получить проверенный серверный путь. Остальные поля сохранения сохраняются. При выключенном флаге это ограничение не действует.
5. Старые открытые лоты без `expires_at` требуют ручной сверки; им не назначается произвольная новая дата. Кнопки старого UI не должны подменять отсутствие нового контракта.
6. Исторические лицензии без квитанции и старые изделия без доказанного мастера требуют согласованного подтверждения; имена/права не выводятся из клиентского состояния.
7. Настоящие гонки нескольких независимых соединений, обратные покупки, перезапуск приложения, проверка двух тестовых Telegram-аккаунтов и включение служебного расписания остаются приёмкой на staging. PGlite выполняет транзакции последовательно и не заменяет такой тест.
8. Размеры усиления мастерских предметов 20–30% проверяются сравнением исходных каталогов и утверждаются владельцем/ChatGPT (T17). Этот пакет измеряет отношения, не меняет баланс.
