# TERRITORY 1.0 · T5–T8: серверный контракт развития

Реализация находится в отдельных исходниках `src/game/progressionV1/` и сценарии `supabase/staged/territory_v1_progression_completion.sql`. Интерфейсы ChatGPT не изменены. SQL не применялся к production; общий переключатель `v1_progression_config.enabled` по умолчанию выключен. Этот пакет обеспечивает серверные операции, но не означает завершённую пользовательскую интеграцию или выпуск.

## Реализовано

- T5: ровно пять настраиваемых активностей, по 20 очков за выполненную, пороги 20/40/60/80/100. Дневные счётчики и недельная сумма ведутся сервером. Неделя начинается **в понедельник 00:00 UTC**, как `weeklyQuests.ts`; клиентское время не используется. Завершения поступают только из доверенной серверной транзакции. Повтор события не прибавляет прогресс. Одна награда на игрока, правило и день/неделю.
- T6: продолжение существующего Благословения. Сохраняются исходный объект и точные заряды. Подтверждённый первый уровень — 3 боя и +50% золота похода (`src/game/progression.ts`). Серверное потребление заряда возвращает бонус для расчёта золота в той же транзакции. Прогресс/уровни и таймер готовы для таблицы правил; неподтверждённый XP за бой не начисляется.
- T7: шесть фондов `level`, `arena`, `blessing`, `adventure`, `artifact`, `dark_energy`, независимые бесплатные/премиальные награды, монотонный подтверждённый прогресс. Премиум активируется только событием доверенного платёжного обработчика и сохраняет идентификатор покупки. Браузер не может объявить покупку оплаченной.
- T8: серверный инвентарь самоцветов, гнёзда существующих предметов Stage3 и Stage8, вставка/снятие, синтез **трёх одинаковых** в один следующий уровень и быстрый синтез всех полных троек выбранного вида/уровня. Смешивание видов/уровней исключено. Остатки сохраняются. Количество гнёзд и эффекты берутся из утверждённого каталога. Пока предмет в escrow аукциона, операции запрещены. При перепродаже гнёзда следуют за экземпляром, снимать камни может только новый владелец.
- Награды используют существующую почту `admin_grants` и атомарный `territory_admin_claim_grant_v2`; нового кошелька или альтернативного механизма начисления нет. Независимые UUID операций обеспечивают повторяемость после закрытия приложения.

Все новые таблицы закрыты RLS и прямыми отзывами прав. Браузер получает только свои данные через два RPC. Старые сохранения, валюты, предметы, профессии и лицензии сценарий не переписывает.

## API для интеграции интерфейса

`authenticatedProgressionClient()` из `src/game/progressionV1/api.ts` связывает клиент с проверенным пользователем. После смены аккаунта старый экземпляр прекращает запросы.

```ts
const client = await authenticatedProgressionClient();
const pending = client.readPending();
if (pending) await client.resume();
const status = await client.fetchStatus();
const result = await client.execute({action: 'claim_blessing', payload: {}});
// result.receipt — неизменяемая квитанция; result.currentStatus — свежие данные.
```

Доступные действия: `claim_reward {ruleId}`, `claim_blessing {}`, `insert_gem {source,itemId,socket,kind,level}`, `remove_gem {source,itemId,socket}`, `synthesize_gem {kind,level}`, `quick_synthesize_gem {kind,level}`. `source` равен `stage3` или `stage8`. Для каждого запроса клиент **до сети** сохраняет UUID/параметры в `localStorage` с ключом пользователя. Неизвестный результат не очищает ожидание. Явная доменная ошибка PostgreSQL `P0001` подтверждает откат транзакции: такой отказ освобождает ожидание, позволяя выполнить независимое действие. Конфликт UUID сохраняет ожидание для проверки. Повтор возобновляет исходный UUID. Неизменяемая квитанция повторного запроса не заменяет актуальное состояние: после неё клиент отдельно загружает свежий статус.

`missingProgressionConfiguration(status)` возвращает конкретные отсутствующие части каталога для согласования. Это диагностические идентификаторы, не готовые тексты интерфейса.

RPC: `territory_progression_status_v1()` и `territory_progression_action_v1(p_action,p_operation,p_payload)`.

Получение награды создаёт письмо и возвращает `grantId`. Финальную выдачу из письма выполняет существующий `territory_admin_claim_grant_v2`, с существующей обработкой save token и серверного сохранения. Не следует начислять награду повторно в React.

## Интеграция доверенных источников

Только сервер может вызвать `territory_private.v1_progression_event(player,event,kind,payload)`. Вызывать **в одной SQL-транзакции** с соответствующим проверенным результатом:

| kind | payload | Эффект |
| --- | --- | --- |
| `activity` | `{activity: id_утверждённого_правила, quantity: число}` | Дневной счётчик, не выше цели |
| `fund_progress` | `{fund, value: проверенное_накопленное_значение}` | Монотонный прогресс фонда |
| `fund_purchase` | `{fund}` | Постоянное премиальное право после подтверждения оплаты |
| `gem_grant` | `{kind, level, quantity}` | Проверенная выдача существующего вида самоцвета |
| `blessing_battle` | `{mode: 'campaign'}` | Потребление заряда, возврат `gold_bonus_bp`; XP только по утверждённому правилу |

`event` — глобальный UUID **одного конкретного эффекта**. Несколько разных эффектов одного боя требуют разных стабильных UUID, например полученных из ID боя и назначения эффекта. Повтор с изменёнными игроком/видом/параметрами отклоняется. Эти события нельзя вызывать отдельным клиентским RPC после локального боя.

`territory_private.v1_gem_equipped_stats(player,stats,equippedIds)` добавляет эффекты гнёзд для подтверждённого сервером списка экипированных UUID. Проверяет владельца, не более семи предметов, отсутствие дублей ID и слотов, escrow и истечение. Для HP сохраняется доля здоровья: `floor(oldHp × newMaxHp / oldMaxHp)`. Поля критов и другие исходные характеристики сохраняются. Вызывать один раз при построении боевого снимка перед VIP. Список экипированных предметов должен приходить из проверенного серверного профиля, а не из запроса браузера. Смена владельца или выставление предмета после утверждения профиля прекращает использование устаревшего списка до обновления профиля.

Для одного предмета доступен `v1_gem_item_stats(player,item)`; совпадение UUID между двумя принадлежащими игроку источниками отклоняется как неоднозначность.

## Старое Благословение

Сценарий не копирует потенциально изменяемый `game_state` автоматически. Доверенный импорт вызывает `territory_private.v1_import_blessing(player,exactLegacyObject,claimedUtcDay)` после проверки снимка. Объект сохраняется целиком в `legacy_snapshot`, его `day` и `charges` не нормализуются и не обнуляются. Повтор идентичного импорта ничего не меняет; другой снимок отклоняется.

Для старого локального `Date.toDateString()` **обязателен проверенный UTC-день последнего получения**, потому что дата без часового пояса не позволяет надёжно восстановить UTC. При его отсутствии импорт отклоняется, а старое сохранение остаётся целым. Для ISO-дня UTC достаточно двух аргументов. Отдельное `last_claim_utc_day` предотвращает повтор получения на границе часовых поясов; исходная строка сохранена. Это ограничение требует реальных данных cutover, его нельзя обходить догадкой о часовом поясе игрока.

## Что требует утверждения и подключения

В production-каталоге намеренно отсутствуют: названия/цели пяти активностей; размеры дневных и недельных наград; все пороги/награды фондов и их цены; XP и коэффициенты следующих уровней Благословения; виды/уровни/эффекты самоцветов и число гнёзд по редкости. Нельзя включать систему, заполняя эти параметры значениями из тестов. Строки с экономическими числами в тесте — исключительно синтетические фикстуры.

Каноническое владение обычным старым лутом ещё не подтверждено серверным реестром; гнёзда такого лута закрыты до проверенного моста владения. Нельзя считать клиентскую копию предмета доказательством. Боевой сервер должен подключить helper характеристик, а источники заданий/фондов — доверенные события. UI и платёжный каталог принадлежат другим пакетам.

Предварительные зависимости сценария: Stage3/Stage5, существующий Stage8, поля escrow Stage8 из пакета аукциона и атомарная почта v2. Сценарий отказывается устанавливаться без атомарного claim RPC. Порядок локальной интеграции: базовые схемы → атомарная почта/аукцион → этот сценарий → боевые/платёжные hooks → утверждённые каталоги → проверка → отдельное решение о включении.

## Проверки

- `node scripts/check-v1-progression-sql.mjs`: реальные PL/pgSQL функции в изолированном PGlite, два игрока, отключённый gate, точное сохранение старых данных, запрет неоднозначного локального времени, понедельник UTC и воскресная граница, пороги/повторы/однократность, премиум/бесплатный треки, потребление Благословения и уровни по синтетическим правилам, синтез/остатки/вставка/снятие, передача владельца, Stage8/escrow/HP-проекция, ACL. Тест загружает **существующий настоящий** `territory_admin_claim_grant_v2` и проверяет финальное начисление письма/повтор без второй выдачи.
- `node scripts/check-v1-progression-client.mjs`: проверка формата, отсутствие каталога, сохранение до отправки, повтор после перезапуска, разделение аккаунтов, повторные квитанции и актуальный статус, повреждённый ответ.
- `npm run typecheck`: пройден при реализации.

Многосессионные конкурентные SQL-тесты на отдельном PostgreSQL, проверка реального старого импорта и мобильная интеграция остаются условиями выпуска. PGlite проверяет транзакционные откаты и повторные запросы, но не заменяет испытание взаимных блокировок двумя соединениями.
