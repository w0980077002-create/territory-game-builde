# Stage8: серверный жизненный цикл предметов, 26.10.2026

Пакет для TERRITORY 1.0, ветка `copilot/stage8-full-cycle`. Production Supabase, main, VIP, алмазы, исторические предметы и скрытый вход в админку не изменялись.

## Реализованный контракт

`supabase/staged/territory_profession_stage8_lifecycle.sql` — **добавочный** SQL для уже установленного Stage8. Он расширяет текущий реестр предметов состоянием экипировки и удаления, использует существующую таблицу квитанций и тот же пользовательский advisory lock `7724`. Новый отдельный инвентарь или механизм изготовления не создаётся.

RPC `territory_profession_stage8_item_action(p_item uuid, p_action text, p_operation uuid)` поддерживает `equip`, `unequip`, `upgrade`, `recycle`, `discard`, `consume`. Сервер проверяет владельца, состояние вещи, срок годности, уровень героя, золото и партии материалов. Повтор UUID возвращает прежнюю квитанцию; другая операция с этим UUID отклоняется. Списание и изменение предмета проходят в одной транзакции. Удалённые предметы сохраняют серверную запись и не восстанавливаются старым сохранением.

Улучшение использует существующие цену, вероятность и линейные прибавки кузницы. Расходуются пригодные партии материалов с ближайшим сроком истечения. Расходники изготовлены на семь суток и списываются по ближайшему сроку годности в пределах рецепта. Добытые ресурсы бессрочны. Разборка изготовленной экипировки не начисляет наград: существующая разрешённая награда относится исключительно к обычной неулучшенной добыче боссов. Новая награда за ремесленные вещи не придумана.

Клиент сохраняет UUID действия в постоянном хранилище отдельно для каждого аккаунта, перед новой операцией подтверждает текущий снимок сохранения, принимает серверную ревизию и обновляет экипировку/инвентарь из реестра. Локальные функции экипировки, кузницы и расходования не могут заменить серверную операцию для Stage8. Изготовленная экипировка участвует в существующем расчёте характеристик и PvE. Расходник PvE применяется после серверной квитанции.

## Воспроизводимые проверки

Все SQL-проверки используют одноразовый локальный PGlite, без подключения к Supabase:

```sh
npm run typecheck
npm run test:professions
npm run test:professions:stage8
npm run test:professions:full-cycle
npm run test:master-license
npm run test:gear-recycle
npm run test:balance
npm run test:economy
npm run test:admin-master
npm run build
```

Полное развитие пяти профессий проходит через реальные RPC от уровня 1 до 300 и проверяет все 37 предметных рецептов, закрытые уровни, лицензию за 50 красных алмазов и прежние пороги XP. Временный приватный допуск тестового владельца ускоряет только тестовые аккаунты. Отдельный обычный аккаунт проверяет неизменность лимита 300 XP/сутки. Ресурсные кошельки заполняются тестовыми фикстурами; это не проверка действующего RPC добычи.

Клиентский тест исполняет настоящий мост с подменённым транспортом: тайм-аут, сохранение UUID, конфликт действий, смена аккаунта, повтор старой квитанции, блокировка двойного нажатия. PGlite выполняет запросы последовательно; одновременные вызовы проверяют результаты сериализации, но не являются нагрузочным испытанием нескольких независимых PostgreSQL-соединений.

Мобильная проверка собирает реальный компонент Stage8 и CSS, подменяя только API и состояние:

```sh
node scripts/build-professions-stage8-preview.mjs
python scripts/check-professions-stage8-browser.py
node scripts/build-stage8-gear-preview.mjs
python scripts/check-stage8-gear-browser.py
```

Все девять обязательных команд и дополнительный `test:professions:full-cycle` прошли. Дополнительно прошли `test:elixir-expiry`, `test:gear-showcase`, `test:workshop`. Проверены 20 сочетаний профессий/ширины и 8 сочетаний ширины/обычной или iOS-разметки для реальных панелей сравнения и кузницы. Это браузерные проверки с изолированным транспортом, без физического Telegram.

## Порядок отдельного серверного включения

1. В отдельной тестовой копии проверить наличие `territory_profession_stage8_items`, `territory_profession_stage8_receipts`, каталога, прогресса, приватной схемы и действующих RPC Stage8. Не запускать заново backend SQL поверх существующей установки. Снять приватную резервную копию текущих игроков, предметов, квитанций и определений изменяемых функций/триггеров.
2. Применить только `supabase/staged/territory_profession_stage8_lifecycle.sql` к копии. SQL не включает флаги выпуска и не переписывает исторические сохранения при установке. Проверить действующие триггеры `players`: порядок и их побочные изменения должны быть проверены на копии, включая сохранение, экипировку, кузницу и награды.
3. Выполнить перечисленные проверки. На копии с реальными контрактами добычи пройти `territory_gather_start → territory_gather_status → territory_gather_claim → execute → item_action → повторный вход/второе устройство`. В репозитории нет определений `territory_gather_status` и `territory_gather_claim`; фикстура кошелька не заменяет эту обязательную проверку. На обычном аккаунте ожидание добычи остаётся четыре часа.
4. Выполнить тест двумя независимыми соединениями PostgreSQL: одинаковый UUID, разные UUID при остатке ингредиентов ровно на одну вещь, параллельное улучшение и смена экипировки, старое сохранение после разборки. Проверить реальные ACL/RLS и отсутствие разрешённых прямых изменений серверных реестров.
5. Устранить блокеры ниже и пройти существующий `territory_stage8_save_cutover_preflight()` в рамках отдельно проверенного серверного включения. Не удалять защитное удержание и не отзывать действующие права сохранения до готовности всех зависимых каналов наград.
6. После отдельного согласованного серверного включения применить проверенный добавочный SQL к рабочей базе и включить согласованный клиент. В этой задаче production SQL не выполняется. Проверить неизменность старых балансов, VIP, профессий, инвентаря и экипировки до/после на втором устройстве.
7. При проблемах остановить новые действия флагом Stage8. Не откатывать базу удалением реестра, квитанций или записей предметов: это уничтожит результаты подтверждённых действий. Исправление или откат функций выполнять по заранее сохранённым определениям и с сохранением журнала операций.

## Блокеры полного завершения

- Четыре существующих товара (`artisan_toolkit`, `artisan_supply_crate`, `artisan_royal_chest`, `engineer_ancient_device`) описаны каталогом как товары для будущих рецептов/аукциона. У них нет утверждённых наград или действующего применения. Пакет не выдаёт за них произвольные материалы или валюту. Поэтому критерий «каждый предмет каталога участвует в механике» пока не выполнен.
- Расходование Stage8 в Арене требует интеграции с её отдельным серверным боевым контрактом. До этого такие расходники там явно блокируются; локальное повторное применение не допускается.
- Действующий preflight перехода сохранений намеренно удерживает выпуск из-за существующих клиентских источников наград и незавершённых серверных PvE/квестовых/достиженческих контрактов. Пакет не объявляет всю экономику серверной и не обходит это удержание.
- Действующая добыча и независимые многосессионные гонки требуют проверки на отдельной полной копии базы, описанной выше. Production не использовался как тестовая среда.

Эти ограничения означают, что пакет закрывает жизненный цикл экипировки и PvE-расходников, но не даёт основания объявлять выполненными все критерии исходного задания или включать весь Stage8 без отдельного серверного этапа.
