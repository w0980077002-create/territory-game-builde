# #366 — сохранность Stage8, подготовлено, не активировано

База: свежий `origin/main` = `dfa207f`. Production SQL, Edge deployment,
миграции живой базы и записи в аккаунты в этой работе не выполнялись.
Пещера, аукцион и «Антиуровень» не изменяются и не включаются.

## Причина и исправление

Путь: server craft → `territory_profession_stage8_items.item_output` →
`fetchStage8Items`/клиентское зеркало → cloud save → gear trigger → forge RPC.
Реестр уже существует и закрыт от клиентской записи. Старый локальный forge
для Stage8 уже запрещён; повторно реализовывать его не требуется.

`owner_cap_state_v1` применял hero cap также к рюкзаку, а gear trigger сначала
вызывал общий normalizer. Поэтому позднего исключения внутри owner cap
недостаточно: характеристики могли быть изменены раньше. Cloud load повторял
cap на клиенте. Refresh ремесла заменял улучшенное зеркало старым реестром.
Снятие/смена экипировки дополнительно создавало новую внешнюю `inv_*` обёртку.

Теперь клиент сохраняет Stage8 mirror при загрузке/миграции, проверяет bag и
worn evidence перед refresh, сохраняет UUID при снятии. Это не даёт права
владения: неизвестный/чужой UUID отклоняется сервером.

Staged `stage8_preserve_state_v3` проверяет исходный и сохранённый JSON до
нормализации, исключает доказанные Stage8 из legacy normalizer/cap и возвращает
канонический item_output. Пропущенные устаревшим устройством предметы
восстанавливаются по реестру. Дубликаты, gear в поясе, чужие UUID и экипировка
выше hero level отклоняются. Старые внешние обёртки поддерживаются по
подтверждённому внутреннему UUID. Обычный legacy guard сохраняется.

Сохранённый уровень выше реестра либо расхождение свойств при том же уровне
блокирует запись и передачу. Нельзя «исправлять» это выбором max/min: нужны
доказательства происхождения. Клиентские поля никогда не обновляют реестр.

Private handoff блокирует двух игроков в порядке UUID, затем предмет, хранит
идемпотентную квитанцию, атомарно передаёт владение и зеркала. Он SECURITY
INVOKER, закрыт для PUBLIC/anon/authenticated и **не является API торговли**:
цен, платежей и публичной возможности передачи не добавлено. Его может вызвать
только будущая отдельно авторизованная серверная операция. Старый replay после
перепродажи не возвращает владение промежуточному владельцу.

Существующий staged forge использует реестр, owner lock, expected level,
operation receipt, серверную случайность и действующие цены/hero cap кузницы.
Каждый исход проверяет точное совпадение сохранённого предмета и кошельков.
Mismatch откатывает весь запрос. Неудачная заточка — подтверждённый игровой
исход с квитанцией; сетевой повтор не списывает второй раз. Legacy baseline
при неудаче не переписывается. Forge отключён до установки обоих save guards
и снова отключается после rollback. История существующих свойств сохраняется,
история заточек записывается в `stage8_forge_receipts_v1`.

использование непустой базы запрещено. CI workflow запускает одноразовый PG17.

Также: `typecheck`, `lint`, `build`, `test:professions:stage8`, `test:balance`,

## Точная граница активации — требуется отдельное разрешение

**Все SQL ниже остаются в `supabase/staged`, автоматического deployment нет.**
Frontend PR сам по себе не устраняет действующий live cap.

1. После отдельного разрешения на live read-only SQL получить свежие
   `pg_get_functiondef` gear guard, owner cap/state, normalizers, forge и список
   player triggers/ACL/RLS. В этой сессии это запрещено прямым поручением.
   Снимок кода репозитория не считается проверкой действующего live SQL.
2. Повторить агрегатный `scripts/sql/stage8_gear_preservation_preflight.sql` и
   расширенную сверку свойств в клоне. Три конфликта (два 5→59, один 1→40)
   известны **из issue #366**, а не из нового чтения базы. Их не исправляли и
   повторно не подсчитывали. Результат выше реестра без forge receipt — HOLD,
   не разрешение понизить или повысить предмет. Нужен индивидуальный разбор
   provenance без записи до отдельного согласованного решения.
3. Проверить текущий реестр/права и все player triggers на свежем клоне;
   прогнать тесты с реальными определениями. Клиентские прямые legacy saves
   всё ещё существуют: это не полный economy cutover/security certification.
4. После согласованного устранения конфликтов и **отдельного разрешения на
   production SQL**, при остановленных writers, одной транзакцией установить
   `territory_stage8_verified_gear_v2.sql`, `territory_stage8_preservation_v3.sql`,
   `territory_stage8_forge_v1.sql`, затем
   `territory_stage8_preservation_activate_v3.sql` (внешний BEGIN/COMMIT собрать
   без вложенных COMMIT из подготовительных файлов).
   Activation блокирует таблицы, проверяет shape текущих функций и все
   сохранённые owned gear, сохраняет исходные функции и заменяет только
   проверенные выражения; неожиданный SQL/provenance останавливает транзакцию.
   Это точка изменения live save behavior. Существующие player/item rows
   установкой не переписываются. Private handoff не получает публичных grants.
5. Проверить production canary по отдельно утверждённой программе и только
   затем разрешить writers/штатный клиентский выпуск. Не применять старые
   auction SQL или общий Stage8 economy cutover ради этого исправления.

Rollback: остановить writers; выполнить
`territory_stage8_preservation_rollback_v3.sql`. Проверяется, что функции после
активации не менялись; исходный код восстанавливается, а специальный BEFORE
trigger блокирует записи владельцев Stage8/Stage8 payload до повторной
активации. Это осознанный fail-closed HOLD, а не потеря вещи. Реестр, история,
квитанции, валюты и уровни **не откатываются**. Удалять HOLD при старом cap
нельзя. Повторная проверенная activation снимает HOLD в своей транзакции.

Владелец отдельно разрешил только чтение. Реальный endpoint из `.env.local` —
`wmyrdpbwlkzsktnhookx`, PG17. Проект с названием territory-game-builde
(`ksikzkrvuuhermhnbycn`) не содержит Stage8-реестра: выбирать по имени нельзя.
Выполнялись только SELECT к metadata/агрегатам; записи и live-вызовы игровых
RPC не выполнялись.

Подтверждено: 324 registry gear, 321 в bag, 3 worn, отсутствующих 0; конфликты
5→59 (2) и 1→40 (1). Для этих UUID нет совпадений ни в private legacy refund
receipts (UUID и stage8_UUID с текущим владельцем), ни в Stage8 forge receipts
(по UUID независимо от владельца). Это отсутствие доказательств в этих двух
журналах, не доказательство подделки и не основание менять предмет.

Live owner_cap_item/state и gear guard сохраняют destructive pipeline;
выражения, заменяемые activation, соответствуют прочитанным live определениям.
Live forge и ready **уже установлены**, ready проверяет только auth.uid().
Поэтому выпуск требует замены действующих forge/ready, а не предположения об
отсутствии RPC. Registry RLS включён, клиентских grants нет (postgres и
service_role); players SELECT/INSERT/UPDATE policies привязаны к auth.uid(),
UPDATE также требует banned=false с WITH CHECK.

Есть 11 пользовательских player triggers, включая economy guard/audit,
материалы, arena belt, legacy masterwork, cleanup, referral, trial reserve,
forge spend capture и leaderboard. Проверка только gear guard не доказывает
совместимость полного production набора. До активации требуется изолированный
прогон полного набора определений/схемы на свежем обезличенном клоне; текущий
fixture не выдаётся за такой клон.

Замечание технического ревью PR о чрезмерном rollback HOLD принято:
HOLD теперь совпадает с опасной областью gear trigger — INSERT либо UPDATE OF
 game_state, attack, defense, max_hp, crit_chance. SELECT/чтение входа не
блокируется; metadata-only updated_at и wallet-only UPDATE не блокируются
этим HOLD. Запись game_state для прогресса/других режимов всё ещё остановится
у Stage8-владельца: безопасно разрешить её при восстановленном destructive cap
нельзя. Если другой trigger присоединяет game_state к UPDATE, операция также
может остановиться. Это ограниченный режим аварийного восстановления, не
полноценный gameplay. Тесты проверяют отказ game_state/attack, допустимость
updated_at/gold и неизменность реестра, затем повторную активацию.

**Результат: NO-GO для текущего общего activation SQL.** Он ожидаемо откажет
на трёх конфликтах. Следующие шаги в порядке: получить доказательства
provenance/резервные снимки для индивидуального решения (без max/min и без
автоматического изменения); проверить полный clone trigger chain; подготовить
точечное согласованное решение конфликтов и повторить preflight; затем в
остановленном режиме writers одной транзакцией установить helpers + обновить
forge/ready + activation. До COMMIT проверить definitions/grants/guards; при
ошибке ROLLBACK всей транзакции. После COMMIT canary только на отдельно
разрешённых тестовых данных, затем клиентский выпуск и открытие writers.
При аварии после COMMIT — staged rollback с суженным HOLD; не удалять HOLD
до повторного включения защиты. Эти опасные шаги данным read-only разрешением
не разрешены и не выполнялись.

## Дополнительная точечная provenance-сверка (read-only, 16.11.2026)

Проверены live `public.admin_grants`, `territory_private.owner_test_gear_v1`,
текущее `game_state`, registry и архивные снимки 08.11/13.11.
Результаты воспроизводятся запросом
`scripts/sql/stage8_owner_admin_provenance_readonly_366.sql`.
Он возвращает только категории и счётчики без player_id/item UUID и не изменяет данные.

- **5→59, weapon, в рюкзаке, upgradeCount=2:** **доказанная административная выдача**.
  Точный UUID/владелец/слот совпадают с `owner_test_gear_v1` (target_level=59),
  а выдача `admin_grants` от 26.10.2026 помечена `claimed_at IS NOT NULL`,
  `adminTestLevel=true`, `equipLevels.weapon=59`. Полный JSON сохранённого
  `equipment` **равен** `admin_grants.payload.adminTestEquipment`; одного
  пользовательского маркера `adminTestLevel` для такого доказательства недостаточно.
  Реестр при этом всё ещё хранит уровень 5. Не переписывать его без отдельного
  контролируемого решения и проверенного clone-скрипта.
- **5→59, weapon, надет, upgradeCount=54:** в snapshot от **08.11.2026**
  этот точный UUID присутствовал **на уровне 5**, в live — 59.
  Точной админской выдачи для UUID нет; соответствующей forge-квитанции нет.
  Это **открытый конфликт**, а не доказанный чит или разрешение откатить.
- **1→40, helmet, надет, upgradeCount=39:** точный UUID/уровень 40
  присутствуют уже в snapshot **08.11.2026** и **13.11.2026**;
  exact admin grant и forge receipt отсутствуют. Это **открытый конфликт**.
- Оба weapon-конфликта относятся к одному игроку, helmet — к другому;
  ни один из этих игроков не является аккаунтом `Esdollars`. Историческая
  админская операция владельца над другим игроком возможна и разрешена,
  но общих записей `adjust` недостаточно для идентификации конкретного UUID.
- `upgradeCount = savedLevel - baseLevel` в двух открытых случаях — признак
  самосогласованного формата сохранения, **не квитанция об оплате**.
  Экономический аудит содержит изменения кошельков, но не устанавливает
  происхождение каждого из этих предметов.

**Важно:** прежнее утверждение «оба предмета 59-го уровня были в snapshot
08.11» неточно для этих UUID: один weapon там был уровня 5.
Также подтверждённая админская выдача относится к **мечу в рюкзаке**,
а не к надетому.

Текущий production activation остаётся **NO-GO**: SQL ожидаемо отвергает
сохранённые уровни выше реестра. Для доказанной админской выдачи подготовить
по-UUID reconcile по защищённой сохранённой квитанции (без общего bypass).
Для двух открытых UUID — доказательный HOLD/отдельный review; не разрешать
неизвестные апгрейды, не удалять, не понижать и не переписывать данные.
Обязательна проверка full live-trigger clone, re-preflight и отдельное разрешение
на любую production-операцию.
