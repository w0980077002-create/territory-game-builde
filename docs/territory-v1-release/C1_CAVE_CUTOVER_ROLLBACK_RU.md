# C1-core Пещеры: контрольный план, не команда на production

Статус: подготовка, **не разрешение на применение**. C1-core ограничен серверной Пещерой: отдельные тёмные камни, проверенный fighter, бой, сохранение и квитанция. Обычный Поход и Испытания остаются на существующем legacy `PveFight`; их серверная авторитетность этим PR не доказана. Пояс в Пещере только для просмотра, без эффекта и списания. Новые расходники и 15 слотов рун не входят в этот cutover.

## Read-only срез 31.10.2026

В момент проверки: 100 `players`, 100 профилей, 100 активных аттестаций, 100 source projections, 128 сессий и 128 settlement, 11 строк прогресса, 14 кошельков тёмных камней с суммой 54. Fighting-сессий и владельцев с более чем одной fighting-сессией — 0; уникальный partial index присутствует. 70 сохранений содержат непустой объект equipped, 49 — хотя бы один ненулевой элемент belt; это не доказательство владения. `combat_profile_is_current_v1` вернул false для 14 игроков, из них 6 уже в очереди и 8 отсутствуют: 13 различий в equipped, 8 в stats, 8 в level (группы пересекаются), 0 различий fighter и 0 отзывов. Значения изменяются во времени; повторить непосредственно перед решением. Никаких ID или личных данных в отчёт не включать. Live RPC прогресса на момент проверки **не** возвращал `active_session_id`; live commit содержал вызов списания тёмного камня. Эта сверка не подтверждает идентичность всего live кода с веткой и не даёт права автоматически исправлять 14 профилей.

## Доказательства и границы

Серверная аттестация содержит владельца, evidence и reviewer, а source связывает её с fighter. Сохранение и `player_inventory`, доступные клиентской записи, не являются доказательством истории вещи. Сохранить ранее подтверждённую силу; новые спорные эффекты не включать; выполнить индивидуальную owner-scoped сверку по независимому доказательству с отзывом и журналом. Предварительно подсчитывать только агрегаты. `belt_N` теряет исходный ID и не является доказательством партии. Никакой backfill из его содержимого. Очередь ранее пополнялась лишь при явном `prepare` владельца; если игрок не вызывал его после изменения профиля, расхождение не попадало в очередь. В staged добавлен идемпотентный `detect_combat_profile_v1(player_id)` для доверенного оператора: он блокирует строку владельца, ставит только отсутствующую запись, не переписывает уже собранные evidence и не меняет имущество. Вызывать по одному владельцу после owner-scoped сверки и отдельного согласования; функция не вызывается автоматически в production.

## Порядок подготовки и проверки

1. Заморозить SHA PR и получить зелёный CI именно на нём. Сверить функции, таблицы, индексы, ACL, определения и существующие production-триггеры с проверенной копией схемы. Снять восстанавливаемые резервные копии и проверить восстановление в изоляции. Ни staged-файлы целиком, ни команды ниже не применять к живой базе без отдельного решения.
2. В одноразовой базе проверить исходные зависимости в порядке `territory_v1_combat_completion.sql` → `territory_v1_adventure_settlement.sql` → `territory_v1_combat_profiles_reconciliation.sql` → `territory_dark_stones_20261030.sql`; последние три файла рассчитаны на существующий completion. Сверить наличие нужных существующих ролей/таблиц и live-определений перед составлением **ревьюируемого минимального** изменения. Completion целиком содержит `CREATE OR REPLACE` и может перезаписать живые функции; применять его поверх production вслепую нельзя. Нынешний staged start списывает только `dark_stone_take_v1`; кошелёк dark-stones должен быть установлен до вызова start, а старые `battleStones` не списываются. Клиенту для межустройственного восстановления нужна версия RPC с `active_session_id`, а Edge — версия из этого PR с проверкой JWT и передачей server-derived UID.
3. На staging повторить проверки PostgreSQL 17 с раздельными соединениями, PGlite, клиентские и RU/EN mobile; проверить фактические auth/RLS, live-эквивалентные триггеры и переключение старых кешированных клиентов. Проверить выбранные для canary профили индивидуально по доказательствам, не подставлять клиентскую экипировку. Не требовать сверки всех 100 как условия одного allowlisted теста. Сохранить исходные значения и отчёт о расхождениях.
4. Перед отдельным разрешением владельца зафиксировать число игроков, наличие и количество сессий по состояниям, квитанций и прогресса, суммы кошельков и число проверенных профилей. Организовать проверяемый ограниченный canary только для готовых профилей, без переноса старого прогресса и без повторной выплаты. Заранее зафиксировать точные версии SQL/Edge/Pages и проверку фактического опубликованного SHA. Telegram WebView и возврат после offline проверить отдельно на тестовом аккаунте.

## Canary

В staged добавлены `canary_only` и закрытая `cave_canary_v1`: при `canary_only=true` commit разрешает новый start только владельцу в allowlist; проверка проходит до списания. Изменять список может только владелец БД, service role имеет только SELECT, клиенты не имеют доступа. `starts_enabled=false` останавливает все новые старты, но не replay/advance/resume. По умолчанию `canary_only=false` сохраняет старое поведение: **нельзя применять полный staged SQL к live и считать его безопасным canary**. Для настоящего rollout атомарно закрыть старты и включить allowlist до предоставления доступа обновлённому клиенту; подготовлены узкий guarded-патч и SQL rollback; они проверены на синтетической PG17-схеме с live-функциями, но требуют отдельного ревью и проверки платформенного ingress/Edge в выделенном окружении.

## Остановка и откат

**Staged start-only gate:** `combat_config_v1.starts_enabled` проверяется сервером в `commit` до списания и создания новой сессии; уже принятые операции, `advance` и `resume` не выключаются. Добавленная колонка по умолчанию сохраняет существующее поведение (`true`), а `enabled` и `settlement_ready` остаются обязательными отдельными ограничителями. Это ещё не установленный production-механизм: нужно подтвердить финальный PG17 CI и ревьюировать guarded SQL-патч относительно текущих live определений перед отдельным решением. Клиентская блокировка кнопки не останавливает старый клиент или прямой API. Общий `combat_config_v1.enabled` проверяется также при `advance`; выключение его при живой сессии способно заблокировать завершение и квитанцию. До canary протестировать на двух соединениях: уже начатый бой, replay и resume продолжают работать, новые start отклонены без списания. Не использовать непроверенный staged gate как готовый production rollback.

При проблеме: остановить только новые старты, сохранить Edge/SQL, кошельки, состояние и operation/settlement receipts; дать начатым боям завершиться или сохранить безопасную возможность resume и повторного получения квитанции. Не удалять/перенумеровывать сессии, не возвращать камни вручную и не повторять награды. Зафиксировать агрегаты до/после, расследовать расхождения. Только после нуля активных и разрешения всех неопределённых операций согласованно восстановить предыдущие версии Edge/SQL и клиент; откат только Pages не откатывает уже подтверждённые операции. Сверить aggregate counts/sums, активные сессии, прогресс и доступность трёх экранов. При несоответствии остановить rollout и не восстанавливать данные поверх более новых без отдельного плана.

## Двухэтапный кандидат для клона

`territory_c1_live_guarded_patch_DRAFT_20261031.sql` требует точных четырёх live MD5, блокирует config от конкурентного старта до проверки нуля активных боёв и включается закрытым (`starts_enabled=false`, `canary_only=true`). Его повторное применение должно отказываться на drift. Phase A `territory_c1_pause_new_starts_DRAFT_20261031.sql` закрывает только start; не останавливает advance/resume/replay. Phase B `territory_c1_restore_functions_DRAFT_20261031.sql` отказывается при активном бою или несовпадении четырёх целевых хэшей, блокирует config, при нуле active переводит `enabled=false`, восстанавливает проверенные baseline SQL функции и сохраняет данные. Тест `territory_adventure_clone_ci` использует синтетические данные и зафиксированные определения функций, не полную production-схему или Edge.

**Внешний gate обязателен:** перед phase B отдельно закрыть ingress, согласовать/разрешить все неизвестные клиентские UUID и проверить отсутствие одновременно выполняющихся или ожидающих запросов; база не видит все клиентские очереди. Отдельно зафиксировать и восстановить опубликованную Edge-версию, проверить совместимость её replay/resume и Pages/старого кэша. Ни закрытие ingress, ни реальный Edge deploy/rollback не проверяются SQL-фикстурой. После phase B не включать боевой сервис до отдельного решения и повторной сверки. Перед любым производственным запуском пересчитать точные MD5 живых функций и остановиться при drift; эти draft-файлы не являются разрешением на изменение production.

## Read-only сверка перед репетицией 31.10

На момент повторной проверки: 100 игроков и 100 verified профилей; 15 stale, из них 6 queued и 9 unqueued, 0 активных боёв, 128 квитанций. Это не разрешение на запись или перенос, показатели динамичны. Шесть включённых пользовательских триггеров players и три RLS policy считаны как метаданные; репетиция использует точные тела шести триггеров и пяти связанных функций, сверяет MD5 и использует синтетические таблицы/строки. Это **не полный schema-only clone**: auth и сопутствующие отношения в фикстуре упрощены, реальный JWT, все зависимости и платформенные настройки не воспроизведены.

Live Edge `territory-combat` version 1, package SHA256 `9c9258ab327c58cfc996cc6b6543597ddb99d5c0fc82b1b66cfacb4b3e3fd983`: три полученных исходника `supabase/functions/territory-combat/index.ts`, `src/game/combatV1/service.ts`, `src/game/idleEngine/index.ts` побайтно совпали с этой веткой на момент проверки. Это сравнение файлов не является тестом live JWT, реального сетевого вызова, Edge deployment/rollback или совместимости будущего SHA. Не делать необязательный Edge deploy, пока не доказана его необходимость.

Доступные проекты не идентифицированы владельцем как одноразовое изолированное staging-окружение; нельзя использовать второй активный проект как disposable без подтверждения его назначения. Для внешнего gate оператору нужно предоставить отдельный non-production Supabase с тестовыми JWT и подтверждённой возможностью закрыть ingress; развернуть там схему без реальных игроков, зафиксировать SHA/версии, воспроизвести pending/replay, phase A, закрытие ingress, drain и phase B/Edge rollback. До доказательства этих шагов нельзя считать production rollback полностью проверенным.

1. Зафиксировать SHA PR и успешные workflow; сверить SHA256 файлов: apply `2649b3a8f3ee74158c087b773376f3ef3a23abaf92561de0c31072d53c33644e`, phase A `d447643de270e46072aad31a540f29ca94a20d4ca4beebd30ee8003500917f6a`, phase B `f464a5fbab04a558639c7f909ffb8026f9e48cf2e4e2f215d9e07564bededa49`. Если файлы или четыре live MD5 изменились, остановиться и повторить ревью. Снять и проверить восстанавливаемый backup, агрегатные counts/sums, старые definitions/grants и все активные/pending операции.
2. В согласованном тестовом окружении закрыть внешний вход и убедиться, что боёв нет. Запустить **только** guarded apply как транзакцию с `ON_ERROR_STOP`; проверить `starts_enabled=false`, `canary_only=true`, пустой allowlist, dark-stone debit, ACL/RLS и сохранение counts/sums. При ошибке транзакции не продолжать. Не запускать полный `combat_completion.sql` поверх действующего сервера.
3. Секретным операторским каналом определить один одобренный тестовый аккаунт и доказать его текущий attested profile; внести только его в private allowlist с evidence, без копирования client-save в права. После проверки сервера и версий открыть starts при сохранённом `canary_only=true`; проверить, что другой аккаунт получает отказ до дебета. При любом расхождении выполнить phase A.
4. В тестовом окружении записать trace одного боя: баланс Dark Stone и обычных камней до/после, start UUID, повтор, ход, receipt, следующий этаж и восстановление после offline/смены устройства. Проверить неизменность активов другого тестового аккаунта; реальные ID и секреты в публичный PR не помещать. Отдельно пройти Поход и Испытания и настоящий Telegram WebView.
5. Остановка: выполнить phase A, удостовериться, что новые старты запрещены, а существующие advance/resume и replay завершаются. После drain доказать закрытие внешнего ingress и разрешение pending UUID, повторить агрегаты; только затем применять phase B. Проверить старые function hashes, выключенный combat, неизменность players/wallets/receipts, возможность replay и согласованную Edge/Pages версию. При drift или неизвестной операции остановиться без отката поверх новых данных.

Edge deploy/rollback не включён в SQL: оператор должен зафиксировать опубликованный digest и протестировать конкретный механизм версии в изолированном проекте. Сейчас live Edge v1 совпадает по трём исходникам, поэтому его замена не является автоматически необходимой. Любые production SQL, изменение allowlist или публикация требуют отдельного решения владельца.
