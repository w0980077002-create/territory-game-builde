Право предназначено всем игрокам с `halloween_2026` и `total_hits > 0` после **2026-11-03 00:00 UTC**, независимо от рейтинга и входа. Другие награды не утверждены. Сезонный `follower_pumpkin_witch_2026` — отдельный от `follower_6`, сразу 100/100, без тренировки. В PvE: `round(62 * 1.05) = 65` атаки и `round(15 * 1.05) = 16` лечения относительно полностью развитого обычного Лесного целителя; разница целых значений составляет 4,84% и 6,67%. Дополнительных PvP, HP, критических или экономических бонусов нет.

## Что находится в PR

- Закрытый ledger с RLS, уникальным `(event_id, player_id, reward_id)` и owner-scoped claim через `auth.uid()`. Сервер проверяет и `ends_at`, и фиксированную дату; клиентское сохранение не доказывает права. Квитанция устанавливает локальное представление; старый активный спутник автоматически не заменяется.
- `snapshot_v1` вычисляет агрегаты и fingerprint участников. `bulk_v1` блокирует строку события, повторно проверяет deadline и snapshot, атомарно вставляет недостающие права, сверяет итог и сохраняет request receipt. Повтор с теми же параметрами идемпотентен. По уникальному ключу двойной entitlement невозможен.
- Admin API после серверной проверки owner token показывает агрегаты. Операторский `halloween_reward_bulk` выключен по умолчанию через `HALLOWEEN_COMPANION_OPERATOR_ENABLED`; его включение — отдельный проверяемый cutover. Каждая авторизованная попытка записывается отдельным RPC до bulk, затем отдельным RPC завершается как успех или ошибка с ограниченным списком кодов. Если процесс прерван или завершение аудита недоступно, попытка остаётся `started`: нельзя считать её ни успехом, ни отказом до сверки receipt. Повтор после неопределённого исхода использует тот же request ID и новую попытку. Таблица аудита и RPC недоступны обычным игрокам, PII не записываются.
- Отдельные `idle.svg` / `blink.svg`, свечение, появление при выборе и независимые эффекты атаки/лечения, привязанные к реальным событиям PvE; карточка лагеря и экран Героя показывают ведьму. Это не подтверждение художественного качества или настоящей Telegram-приёмки. Скриншоты в `halloween-fixture/` сделаны из React fixture, без Auth и production.
- PostgreSQL 17 CI использует изолированные тестовые часы и применяет точный staged SQL. Дополнительный тест получает подписанные JWT двух пользователей из изолированного Supabase Auth и проверяет их через отдельный PostgREST с публичными JWKS Auth. На SHA `8414530` прошли проверка подписи, дедлайна, неучастника, чужого аргумента, повторного claim, корректно подписанного истёкшего токена и двух Auth-сессий. Изолированный stale state менялся тестовым SQL: это проверяет независимость ledger, но не реальную очередь сохранений старого клиента. Это тестовые сервисы, не production. Реальный игровой клиент на двух устройствах, старый клиент, Telegram WebView и визуальная приёмка остаются release gates.

## Защищённый порядок выпуска и остановки

1. До любых действий в production: завершить ревью, финальный PG17/RLS/параллельность и Auth/JWT на текущем SHA, полную проверку клиента и Telegram. Проверить права, функцию аудит-статуса, поведение при обрыве между тремя отдельными RPC и UI статуса на тестовом окружении. `CODE READY` не означает `LIVE GRANTED`.
2. Только при отдельном одобренном cutover установить серверную часть, проверить негативные сценарии, затем совместимый клиент. Операторский флаг оставить выключенным до закрытия рейда и отдельной проверки готовности. До 03.11 UTC claim не выдаёт право, snapshot/bulk отклоняются сервером.
3. После закрытия сохранить read-only итог рейда и агрегатный `snapshot_v1`: `eligible`, `granted`, `pending`, `unexpected`, `duplicates`, `digest`, время и ревизию SQL. Не публиковать ID игроков. При `unexpected != 0`, несоответствии данных или неподтверждённом audit status — остановиться.
4. В защищённой операторской среде задать `TERRITORY_SUPABASE_URL`, `TERRITORY_SUPABASE_ANON_KEY` и `TERRITORY_OWNER_TOKEN` через штатное безопасное хранилище; не записывать токены в файлы или журнал. Сначала установить `umask 077`, затем запустить `python3 scripts/halloween-reward-operator.py preview > /tmp/halloween-preview.json`, чтобы файл был доступен только владельцу. После ручной проверки снимка и флага использовать `python3 scripts/halloween-reward-operator.py grant --preview-file /tmp/halloween-preview.json --request-id UUID`, где UUID сохраняется для безопасного повтора. `reconcile` получает текущую сверку. Клиент вызывает owner-authenticated action `halloween_reward_bulk` и передаёт точные `requestId`, `eligible` и `digest` из снимка. Не вызывать bulk напрямую из SQL: это обходит отдельный журнал попыток. Внутри операции событие блокируется и snapshot повторно сверяется; изменившийся snapshot требует нового preview. Записать request ID и server receipt в защищённый журнал. Операторский флаг включается только на время операции.
5. Повторно получить snapshot и audit status; проверить `eligible = granted`, `pending = unexpected = duplicates = 0`, отсутствие незавершённых попыток и объяснение ошибок. Повтор request ID с теми же параметрами безопасен; новый снимок и новая операция позволяют дозачислить отсутствующих. До каждого запуска проверять утверждённый состав наград.
6. При отказе выключить операторский флаг, сохранить в защищённом журнале request ID, код и время; не печатать личные данные. Проверить receipt и статус попытки: сбой после commit может оставить `started` или ошибку соединения при уже выданной награде. При `unfinished > 0` повтор блокируется: после отключения флага и подтверждённого завершения всех незаконченных вызовов оператор в защищённой DB-сессии сопоставляет `attempt_id`/`request_id` записей `state = 'started'` с `halloween_companion_bulk_receipts_2026`. Затем отдельным вызовом `territory_halloween_companion_attempt_finish_v1(attempt_id, request_id, NULL)` отмечает успех только при наличии receipt; при отсутствии receipt отмечает `unavailable`. Функция сама не разрешает успешный итог без receipt. Снова проверить audit и snapshot. Не удалять законные права и не откатывать player saves; устранить причину, сделать новый preview и идемпотентно повторить. Встроенный журнал охватывает вызовы через operator action; прямой SQL и отказы до авторизации им не покрыты и должны быть запрещены операционным доступом/отдельным инфраструктурным аудитом.

Legacy PvE-бой остаётся клиентским: серверный entitlement не является серверной аттестацией всего боя. Никакой исходный рейтинг, HP босса, VIP, валюта, инвентарь или активная Боевая корова не изменяются механизмом выдачи.
