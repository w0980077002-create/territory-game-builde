# TERRITORY 1.0 — T13/T14: серверные контракты VIP и Stars

Изменения подготовлены в отдельной ветке. Production, реальные платежи, webhook бота, секреты и публикация не изменялись. SQL находится только в `supabase/staged/territory_v1_monetization_completion.sql`.

## Что реализовано

- Постоянный `players.vip_level` (0–10) и временный VIP из существующего Колеса фортуны сохраняются. Новые накопленные VIP-баллы учитываются отдельно от уровня и никогда не снижают существующий ранг.
- Таблица подтверждённых VIP-рангов задаёт пороги и прибавки атаки/защиты/HP в basis points. Одна формула используется для PvE/PvP; текущее HP сохраняет долю от максимального, погибший герой не оживает. Бонус применяется один раз к исходному серверному снимку; сохранённые базовые характеристики не переписываются.
- `territory_vip_status_v1()` возвращает подтверждённые правила, баллы, действующий ранг, срок временного VIP и серверное время. `bonusesConfigured=false` явно означает отсутствие подтверждённого бонуса.
- Создание Stars-заказа по SKU и UUID операции, неизменяемый снимок цены и награды, получение настоящей invoice link через Bot API. Браузер не передаёт цену или размер награды.
- Precheckout сверяет связанного Telegram-пользователя, payload, `XTR`, сумму, срок и доступность сервиса. Один заказ принимает только один `pre_checkout_query.id`; повтор того же запроса безопасен, другой запрос отклоняется, чтобы повторно открытая invoice link не дала второй платёж за один заказ.
- Только webhook с `X-Telegram-Bot-Api-Secret-Token` вызывает серверную выдачу. `invoiceClosed('paid')` и любые клиентские callbacks ничего не начисляют.
- Выдача, VIP-баллы, новый ранг, квитанция и уникальный Telegram charge ID фиксируются одной транзакцией PostgreSQL. Повтор webhook не повторяет награду. Другой аккаунт/заказ не может повторно использовать charge ID.
- Уже оплаченный и ранее разрешённый precheckout доставляется после закрытия приложения, истечения срока заказа, изменения каталога или выключения новых покупок. При ошибке Edge Function возвращает 503 для повтора Telegram; транзакция полностью откатывается.
- Валюты пишутся в существующие `players.gold/gems/game_state.player`; при наличии Stage3 также атомарно обновляется уже проверенный `territory_wallet_v1` с обязательным совпадением балансов (без автозаполнения или переопределения старого учёта); красные алмазы также сверяются с существующим закрытым кошельком мастер-лицензии. Несогласованное старое состояние не «исправляется» догадками: выдача откатывается с ошибкой для разбирательства. Инвентарь, никнейм, благословение, неизвестные поля и старый VIP сохраняются.

## Интеграция без изменения чужого UI

- `src/game/monetizationV1/vip.ts`: `resolveVip`, `applyVipCombatStats`, `adaptIdleVipStats`. Последний сохраняет вероятности crit/dodge/block в формате 0–1, не смешивая их с процентами старого `PlayerStats`.
- Серверный расчёт снимка боя: `territory_private.vip_combat_stats_v1(playerUUID, statsJSON)`. Вход содержит целые `attack/defense/hp/maxHp` и любые дополнительные поля; выход сохраняет дополнительные поля. Максимум каждого вычисленного стата — 2 147 483 647. Использовать только один раз при создании боя, до вычисления результата; обе стороны PvP обрабатываются одинаково.
- `src/game/monetizationV1/stars.ts`: типы и клиентский транспорт. Действия Edge Function: `catalog`, `invoice {sku,operationId}`, `status {orderId}`. После `fulfilled` UI должен безопасно перечитать существующее cloud save; нельзя накладывать старую квитанцию поверх более нового прогресса или локально прибавлять награду.
- Webhook: `/functions/v1/territory-stars/webhook`. Invoice/status/catalog требуют действительный Supabase access token через `getUser`, webhook требует секрет Telegram. Для будущей публикации этой отдельной функции потребуется `verify_jwt=false`, поскольку Telegram не присылает Supabase JWT; проверка пользователя/секрета выполняется в обработчике. Текущий `config.toml` не изменён.

## Необходимые настройки и ограничения

Подтверждённых XTR-цен и собственных VIP-порогов/коэффициентов в источниках нет. **В SQL не вставлены ни один продаваемый набор и ни один ранг.** `payments_enabled=false`, `vip_enabled=false`. Заданные в автотестах числа — только тестовые фикстуры; это не продуктовый каталог.

До отдельного релиза нужны утверждённые SKU с содержимым/ценой/источником, VIP-пороги и бонусы, проверенный серверный cutover сохранений/кошельков, секрет webhook, доступ сервера к Bot API и тестовая оплата Telegram. Текущие реализованные содержимые набора: золото, синие/красные алмазы, VIP-баллы и премиальный доступ к одному из шести фондов (`level/arena/blessing/adventure/artifact/dark_energy`). Допустим набор только с доступом к фонду, но цена Stars всегда положительная. `premiumFund` сохраняется в неизменяемом снимке заказа; выдача вызывает `v1_progression_event(player, md5(orderId||':fund')::uuid, 'fund_purchase', {fund})` в той же транзакции, что квитанция оплаты. Отсутствующий или выключенный модуль progression отклоняет новый precheckout до списания Stars; если модуль стал недоступен после разрешённого precheckout, выдача полностью откатывается для безопасного повтора; оплаченный доступ не теряется. Изменение каталога не меняет ранее созданный заказ. Продажа предметов/временного VIP/профессий не объявляется работающей через этот API.

Зависимости SQL: текущие `public.players`, `territory_private.fortune_vip_v1`, `fortune_inventory_v1`, `territory_master_license_red_wallet_v1`. Скрипт не переносит и не пересчитывает существующие данные игроков. Конфигурация и каталоги закрыты от браузера, все новые таблицы имеют RLS; служебные RPC выдачи разрешены только `service_role`. Необходима отдельная проверка staging роли/грантов/политик перед применением.

Возвраты Stars не запускаются автоматически. До продажи нужен согласованный процесс поддержки: идентификация по charge ID, проверка `refundStarPayment`, журнал возврата и обработка уже потраченных цифровых товаров без произвольного изъятия старого прогресса. Клиентская кнопка «оплачено» не считается подтверждением. Настоящие Telegram invoices, webhook delivery и многосоединительные гонки не проверялись локальным PGlite.

## Архитектура отдельного внешнего веб-магазина

Внешний магазин — отдельный проект и публикация. Отдельный origin и серверный каталог, подтверждение связанного игрового аккаунта одноразовым короткоживущим кодом, серверные заказы и провайдерские receipts, проверяемая финальность транзакции, уникальный `(provider, network, chain, transaction, event_index)` и атомарное исполнение через тот же игровой учёт. Курс, подтверждения сети, токен и адрес контракта берутся только из утверждённой конфигурации; GRAM и Toncoin не отождествляются.

Статусы: создан → ожидает оплаты → подтверждён провайдером → выдан; отдельно возврат/разбирательство. Только подписанный webhook или проверка API/сети сервера переводит заказ в подтверждённый. Повторная доставка выдаёт одну квитанцию, несовпадение актива/суммы/получателя отклоняется. До запуска нужны отдельное утверждение платёжного канала, правил магазина и платформы, каталог, юридические/региональные требования и проверка связывания аккаунтов. Никаких криптоплатежей, кошельков, депозитов, выводов или денежных выплат этот пакет не включает.
