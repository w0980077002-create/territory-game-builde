## Сначала изолированный стенд

1. Создать новый Supabase-проект. Не считать существующий проект с похожим названием стендом. Перенести проверенную действующую схему без строк игроков/auth, секретов, почтовых cron-задач и рабочих интеграций. Не запускать все старые миграции/все staged файлы вслепую: в репозитории есть неподготовленные переходы.
2. Настроить Telegram-авторизацию из текущей рабочей версии в тестовом проекте, с **отдельным ботом**. Его TELEGRAM_BOT_TOKEN/BOT_TOKEN хранить только в Edge Function. SUPABASE_URL/ANON_KEY/SERVICE_ROLE_KEY относятся только к тестовому проекту. SERVICE_ROLE_KEY и bot token никогда не добавлять в VITE_* или артефакт.
3. Проверить зависимости, применить только новый SQL целиком в транзакции. Права выдаются только authenticated на RPC; обе таблицы закрыты RLS, политики прямого доступа отсутствуют. Пустой список тестеров блокирует RPC до любого изменения кошелька.
4. После первого входа выбранного тестера в тестовый проект добавить **его UUID из тестового players**, не Telegram ID, административной SQL-сессией:

```sql
INSERT INTO territory_private.monopoly_testers_v2(player_id)
VALUES ('UUID_ТЕСТОВОГО_ИГРОКА') ON CONFLICT DO NOTHING;
```

Чтобы закрыть доступ, удалить только его запись из monopoly_testers_v2. Не изменять admin-api, пароли, главного бота или скрытый вход.

5. Для сборки использовать `.github/workflows/monopoly-test.yml`, manual ref `review/monopoly-safe-test-20261017`, environment `monopoly-test` с двумя staging secrets. Скрипт сборки требует явные переменные, отвергает оба известных существующих Supabase проекта и secret/service_role ключи. У JWT anon дополнительно сверяет project ref. Новый publishable key не содержит ref: принадлежность ему проверяет владелец при настройке environment.

Если ручной workflow ещё не виден на default branch, с авторизованным GitHub CLI:

```bash
gh workflow run .github/workflows/monopoly-test.yml --ref review/monopoly-safe-test-20261017
```

Если GitHub требует наличие workflow на default branch, **не сливать PR** ради этого: локально задать две VITE-переменные тестового проекта и выполнить `node scripts/build-monopoly-test.mjs`, затем упаковать `dist-monopoly-test/`. Без настроек тестового проекта сборка намеренно останавливается.

6. Тестовый HTTPS-хост должен раздавать весь каталог `dist-monopoly-test` с вложенным `/territory-game-builde/`; root index перенаправляет туда. Mini App URL отдельного бота: `https://ТЕСТОВЫЙ-ДОМЕН/territory-game-builde/`. Рабочую Pages публикацию не переключать. Не использовать production secrets на PR. Артефакт сам по себе не доступен в Telegram и ничего не развёртывает.
7. Пройти Android-чеклист владельца, в том числе реальные серверные RPC и двойные окна одного пользователя. Тестовые значения не переносить обратно в рабочую игру.

## Порядок возможной рабочей установки — ТОЛЬКО после отдельного подтверждения

1. Зафиксировать одобренные commit и SHA-256 SQL; повторить read-only preflight и проверить отсутствие конфликта имён. Сверить ограничения, функции, роли и RLS. Если обнаружено различие — остановиться.
2. Подтвердить свежую полную резервную копию рабочей БД с возможностью восстановления (players, auth-связи, hall_accounts/sessions/history и остальная схема). Проверить восстановление в отдельном защищённом окружении. Не выгружать сохранения в Git/PR/артефакты.
3. До SQL зафиксировать в защищённой операторской записи количество игроков и кошельков и целостность сохранений; после сравнить. Во время сравнения остановить игровые записи в согласованном окне либо сравнивать в согласованном снимке — обычная активность иначе изменит контрольные суммы.
4. Убедиться, что рабочий frontend всё ещё старый. Выполнить **один файл** SQL целиком. В нём BEGIN/COMMIT, lock_timeout 3s, statement_timeout 30s; ошибка откатывает весь файл. DDL создаёт только две пустые таблицы и два новых RPC: не обновляет players, не сбрасывает кошельки, не заменяет hall RPC. Повторная установка намеренно завершается ошибкой, а не перезаписывает версию.
5. Проверить создание/RLS/GRANT, повторно проверить зависимые функции, количество строк и сохранения; выполнить Supabase security advisors. Не вызывать игровые RPC под чужими auth.uid и не начислять тестовые деньги рабочим игрокам. Открывать закрытый рабочий тест только после согласия владельца: он расходует настоящие билеты и начисляет настоящее золото.
6. Не сливать и не публиковать клиент до отдельного решения. Список приглашённых остаётся закрытым; общая публикация потребует отдельно проверенного изменения доступа.

## Возврат без потери данных

Если установка падает до COMMIT — транзакция откатывается, не повторять частями. Если установленный тест требуется остановить — оставить прежний frontend, убрать доступ тестеров или отозвать EXECUTE на новом RPC в согласованном окне. Прогресс и журнал не удалять. Не DROP CASCADE и не восстанавливать старую копию поверх живых игроков: это уничтожит более новые достижения. Существующие билеты/золото после уже выполненных ходов не «откатывать» общим UPDATE; спорные операции разбирать по журналу. Ошибка клиента лечится возвратом клиентской версии, а не обнулением сохранений.

## Что подтверждают тесты и что ещё не проверено

Локально PGlite: установка сохраняет существующие players и кошельки; allowlist закрыт; anon/прямой доступ к таблицам запрещён; игрок не может завершить чужой ход; повторный start при активном ходе возвращает тот же token без списания; повторный finish не добавляет золота/кругов; подарки/задания/круги однократны; ×10 списывает 10 один раз; лимит 1000 золота; общий кошелёк с админскими 250 билетами; настоящая hall_claim переносит pending_gold в player.gold, сохраняя inventory/gems/redGems/battleStones/forgeMaterials; повторное получение золота не проходит; другая активная игра не заменяется.

Это проверки последовательных повторов и SQL-блокировок в локальном Postgres-совместимом движке, а не доказательство поведения двух сетевых клиентов одновременно. Не выполнены: конкурентный тест на настоящем Postgres/Supabase, авторизованный end-to-end со staging, браузерное визуальное тестирование 320/390/768px, Android Telegram WebView, настоящая плохая сеть, аппаратный Back, Telegram lifecycle, английский язык и reduced motion на устройстве. Chromium и Vite заблокированы sandbox; эта граница явно сохраняется в PR.

Дополнение: отдельное получение ресурсов сверяет updated_at и точный сохранённый snapshot, затем атомарно обновляет gems, forge_materials и game_state (battleStones, forgeMaterials, inventory). Суммы и свойства предметов задаёт сервер. Клиент предварительно сохраняет состояние, а после подтверждения перезагружается, не обновляя общие кеши autosave вручную; старые записи отклоняются CAS. Блокировка players FOR NO KEY UPDATE совместима с FK вставкой истории зала. Красные алмазы не начисляются. См. [каталог наград и исходная ошибка CI](REWARDS_AND_CI_RU.md).
