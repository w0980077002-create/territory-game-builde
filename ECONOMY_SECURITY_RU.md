## Подтверждённые проблемы

1. `cloud.ts: saveCloudSave` записывает весь `game_state` и `gems` без проверки версии. На рабочей базе роль authenticated имеет права UPDATE и INSERT этих колонок. RLS ограничивает строку владельцем, но не подтверждает законность баланса. Старое сохранение возвращает списанные 1000 алмазов; собственный баланс можно подделать напрямую.
2. Два устройства могут целиком перезаписать инвентарь, награды и прогресс друг друга. Простое объединение по максимуму восстановит потраченные предметы; складывание снимков удвоит награды. Поэтому автоматическое такое объединение недопустимо.
3. `ProfessionsScreen.tsx` расходует ресурсы и повышает мастерство локально. `territory_resource_wallet` при крафте не уменьшается. Следующее получение добычи заменяет локальное количество серверным накопленным количеством и возвращает уже потраченные ингредиенты.
4. Серверная таблица `territory_profession_unlocks` запрещает повторный выбор, а блокировка строки игрока не допускает двойного списания через RPC. Однако клиентский `game_state.professions` можно переписать независимо от неё. Профессии старого формата без записи в таблице требуют бесплатного переноса, а не повторной покупки. На момент чтения число таких записей и конфликтов равно нулю; миграция всё равно обрабатывает этот случай.
5. Начисления заданий/достижений, ежедневных наград, писем, испытаний, монополии и покупки сейчас вычисляются в браузере. Проверять только разницу балансов, клиентские claimed/current или клиентский список наград недостаточно: эти поля тоже подделываются.
6. Ошибка сети после RPC не доказывает откат транзакции. Сообщения «ничего не списано/начислено» были недостоверны; исправлены без изменения правил игры.

## Что уже защищено в действующей базе

`territory_gather_start` и `territory_gather_claim` используют одну транзакционную advisory-блокировку игрока. Первичный ключ допускает одно задание. Сервер проверяет время; получение удаляет готовое задание и увеличивает кошелёк в одной транзакции. Повторный claim без нового готового задания не выдаёт награду. У authenticated только SELECT на кошелёк/задания/открытые профессии.

Найдено небольшое несоответствие точной длительности: два отдельных вызова clock_timestamp при старте дают интервал между started_at и finishes_at чуть меньше четырёх часов. В предложенной миграции оба времени вычисляются от одного серверного момента.

## Подготовлено, но не включено

Миграция `supabase/migrations/20261013211739_economy_revision_and_professions.sql`:

- сохраняет старые открытые профессии без списаний; при конфликте откатывает всю миграцию вместо произвольного выбора;
- добавляет серверную версию сохранения; изменение game_state/gems, в том числе существующим RPC, повышает её;
- добавляет атомарный commit для доверенного серверного обработчика с проверкой версии, постоянства профессии и диапазона мастерства;
- записывает результат операции вместе с уникальным идентификатором: точный повтор возвращает прежний результат; тот же идентификатор с другим содержимым отклоняется;
- при устаревшей версии отклоняет запись целиком, сохраняя актуальный инвентарь и прогресс;
- запрещает anon/authenticated вызывать доверенный commit; service_role остаётся только на сервере;
- исправляет точность четырёхчасового интервала.

**Это инфраструктура, а не готовая защита всех операций.** `territory_commit_validated_state` не проверяет происхождение награды: его разрешено вызывать только после серверного расчёта действия. Нельзя создавать публичный обработчик, просто пересылающий туда присланный клиентом state. Прежние права записи пока намеренно не отозваны, клиент `cloud.ts` пока не переключён. Поэтому старая уязвимость остаётся действующей даже при отдельном применении этой миграции. Не применять её как самостоятельное исправление.

## Обязательная оставшаяся работа до выпуска

1. Реализовать серверные обработчики всех источников/расходов валюты, крафта и мастерства. Серверные каталоги наград и рецептов; серверный учёт выполнения, включая подтверждение результатов боёв без изменения боевого баланса; уникальность награды по источнику/периоду. Существующие награды администратора сохранить совместимыми.
2. Крафт должен транзакционно уменьшать серверный кошелёк и создавать предмет с мастерством, общей версией и квитанцией. Просто уменьшать локальный стек или затем зеркалировать кошелёк нельзя.
3. Клиент должен отправлять действия с постоянным operation_id, а не произвольные балансы/инвентарь. После неопределённого сетевого результата повторять тот же operation_id. Сохранять неподтверждённые действия до ответа; конфликт версии обрабатывать без потери локальных намерений и без повторной награды.
4. После переноса всех действий закрыть INSERT/UPDATE защищённых колонок для клиентских ролей, включая game_state и создание нового персонажа. Проверить отдельно админские RPC, переходную Telegram-авторизацию и старт новых героев. Не менять админку.
5. Снять резервную копию и проверить миграцию/обратную совместимость на отдельной тестовой базе. Получить отдельное разрешение владельца на рабочую миграцию. Не обнулять старые кошельки, предметы или персонажей; спорные накопления не исправлять массовым сбросом.
6. Только после полного перехода убрать блокировку `economy-release.json`, запустить Pages и проверить SHA опубликованной сборки.

## Проверки

`npm run test:economy` и `npm run test:saves` запускают одну изолированную SQL-серию на PGlite (PostgreSQL в WASM), без сети к Supabase. Фикстура содержит только определения четырёх RPC, прочитанные из рабочей схемы, без данных игроков. Тесты сначала воспроизводят два текущих обхода на искусственных строках, затем проверяют предложенный механизм версий/квитанций, запреты доступа, сохранение профессии, 4 часа, повторный claim и следующий старт.

Это не нагрузочное испытание параллельных соединений и не доказательство защиты текущего клиентского пути. Перед рабочим применением необходимы интеграционные тесты полного пути и конкурентных транзакций на обычном PostgreSQL/Supabase.

Локально прошли: typecheck, build, SQL-проверки экономики/сохранений, professions (5 профессий, 17 рецептов, потолок 300), balance, feature-separation, mobile-home и три имеющиеся серии Telegram-auth. Предупреждение Vite о размере чанка не является ошибкой сборки.

Pages workflow теперь проверяет TypeScript и регрессии перед сборкой. При `economy-release.json.ready=false` сборка проверяется, но deploy пропускается. Это предотвращает случайный выпуск незаконченного перехода. SQL не применяется ни одним добавленным workflow.

Ничего не опубликовано игрокам; рабочая база, авторизация, админка, характеристики героев и боевой баланс не изменялись.
